# Release notes and What's next (User Guide, section 2 of 8)

These notes describe the releases of `migrate-auth`, the newest first. They are updated with every release.

## Version 0.6.1-alpha

This is an **alpha** release. It follows `0.6.0-alpha` and carries one set of changes: two corrections to C# findings that were false alarms, a new Low-confidence report for JavaScript and TypeScript, and the C# corrections described below. The detection catalog of this release is version `1.45.1`. The known issues 42 to 47 below belong to this release; the known issues 1 to 41 are listed with the notes of `0.6.0-alpha`. There is no separate release between `0.6.0-alpha` and this one: every change that is listed here is new in this release.

Use an alpha release to assess repositories and to give feedback. Read every finding and recommendation before you act on it: the tool locates Basic Authentication and proposes a migration, and you decide.

**A repository that you assessed with `0.6.0-alpha` or an earlier release should be assessed again with this release.** Some findings that the earlier release reported at High or Medium are now reported at Low or are gone, some code is now reported at Low that was not reported at all, and the C# findings described at the end of the list below are new or at a different level. A session saved by an earlier release is not resumed; see known issue 6.

### Changes in 0.6.1-alpha, from 0.6.0-alpha

**No longer reported at High or Medium.**

- **A colon-joined value that is encoded to Base64 is reported at Low, not at Medium, when neither half is named like a credential.** In C#, a pair such as a width and a height, a host and a port, a start and an end, or the two parts of a composite key, joined by a colon and encoded, was reported at Medium as an encoded user name and password. It is now reported at Low, for manual review, with no flow and no recommendation, and the report gives the reason: the two halves are not named like a user name and a password. A pair in which at least one half is named like a credential (`user`, `login`, `account`, `email` or `mail` for the first half; `password`, `secret`, `credential`, `token`, `pass`, `pwd` and similar words for the second) is still reported at Medium. A name does not count as a credential name when the word is directly followed by an identifier word such as `Id`, `Guid`, `Number`, `Index` or `Code` (`accountId`, `user_guid`), so a pair of two such identifiers is reported at Low as well. See [Part A for C#](../migration/part-a-csharp.md#cs-009).
- **C# code in a block that the file's own conditional-compilation symbols switch off is reported at Low, not at its ordinary level.** The tool reads the `#if`, `#elif`, `#else`, `#endif`, `#define` and `#undef` lines of the file. A header write, a credential or any other construct in a block whose condition the file makes certainly false, such as `#if false`, or such as a symbol the file never defines, is reported at Low for manual review, and the report gives the reason: the code sits in a block that the file's own symbols switch off. Before, such code was reported as if it were built, at High or Medium. Symbols that a build normally supplies (`DEBUG`, `RELEASE`, `TRACE`, the framework symbols that start with `NET`, and the platform words with or without a version) are never treated as undefined, so code under them keeps its level, and so does the `#else` branch of a condition that is false. A file that holds an interpolated raw string, or a raw string opened with more than one `$`, is not read for directives at all. See [Part A for C#](../migration/part-a-csharp.md#how-confidence-is-assigned).

**Newly reported at Low.**

- **The two new reasons.** The `lowReasons` values gain `neutralOperandPair` (a colon-joined pair whose halves are not named like a user name and a password) and `inactivePreprocessorRegion` (the match sits in a block the file's own conditional-compilation symbols switch off). The report says each in words on the "Low because" line, and the JSON data file carries the value; see [Using the tool](01-using-the-tool.md). A finding with either reason is not a clean result: it is present in the text and needs a review.
- **An `Authorization` header whose whole value is read from a settings property is reported at Low in JavaScript and in TypeScript (`JS-019`).** A header written as `headers: { Authorization: settings.serviceAuthorization }`, where the same file assigns a property of that name (a name that ends with `authorization`, in any letter case) from an environment variable (`process.env`, `import.meta.env`, `Deno.env.get` or `Bun.env`) whose name carries a credential word, is reported at Low for manual review, with no flow and no recommendation: the scheme is inside the variable, so the tool cannot tell from the code whether it is Basic. Before, such a header was not reported at all. A site is not reported when an explicit `Bearer` value for an `Authorization` header is written within thirty lines of it, before or after. A TypeScript file reads the same class, so a TypeScript finding shows `JS-019` with TypeScript as its language. JavaScript now has nineteen pattern classes, seven of them always Low, and TypeScript twenty-one. See [Part A for JavaScript](../migration/part-a-javascript.md#js-019), [Part A for TypeScript](../migration/part-a-typescript.md#js-019) and known issue 42.

**Declared as not covered, now stated explicitly.**

- **Two JavaScript and TypeScript forms are listed as not covered, each in its own entry.** After a report on `0.6.0-alpha`, the catalogs of both languages declare these two forms in explicit entries; before, they were covered only by more general entries. They produce no finding at any level. The first is a user name and a password joined by a colon and handed to the project's own encoder function, in a file that never names the Basic scheme: the tool recognizes the standard encoders only, and a function of the project's own gives it nothing to anchor on. The second is a credential, options or header object chosen by a selector (an enumeration, a switch or a map) and returned from a function, with no client visible in the same statement. Search for both by hand with the searches in [Part A for JavaScript](../migration/part-a-javascript.md#declared-unsupported-coverage) and [Part A for TypeScript](../migration/part-a-typescript.md#declared-unsupported-coverage). Several forms of a settings property are declared as not covered as well (a property under another name, bracket access, destructuring, optional chaining, an object shorthand, a call as the receiver, several members on one line, a class field, a property filled from a call, an alias or another file, an environment variable that is named for a host or a port, and a property whose fallback names a scheme); in TypeScript, a non-null mark or a cast after the property or the environment read also takes the header out of the reading. See known issue 43.

**Reported at Low although the code may be genuine.**

- **A genuine colon-joined user name and password whose halves are both named neutrally is reported at Low.** The tool judges a pair by the names of its halves. A real pair held in two names that carry no credential word, or in names that use a credential word the tool does not list, is reported at Low for review and not at Medium, so it does not count among the findings you migrate first. Read every Low finding of a colon-joined pair before you dismiss it.
- **A genuine use that is built only under a symbol that the project file or the build command defines is reported at Low.** The tool reads the symbols the file itself defines and does not read the project file or the build command. A block under a symbol that only the project defines is read as switched off, and a header or a credential in it is reported at Low although it is part of the build. Check the project's build settings before you dismiss such a finding. This holds as well for a build symbol outside the list of symbols the tool treats as supplied by a build.

**The C# corrections.**

- **A call that passes a user name and a password to the Relativity test helper is found in C#.** A call of the method `GetProxy` with one type argument and two arguments, as in `helper.GetProxy<IExampleService>(userName, password)`, is reported at High, and at Medium in test code, with a recommendation for each flow. The tool cannot tell from the call alone that the two arguments are a credential, so it reports the call only when one of three signs is present: the second argument is named like a password, the first argument is named like a user, or both arguments are written as text. A second argument named like a token or a key is never reported. **Declared limits:** a call with no type argument, with another number of arguments, with named arguments written in reverse order, or with an argument more complex than a name, a member access, a single call or an index is not reported, nor is a call whose two arguments carry no sign of a user or a password in their names. Search for `GetProxy` and review each call by hand. A call of an unrelated method with the same name and arguments that look the same can be reported, and should be dismissed on review. See [Part A for C#](../migration/part-a-csharp.md#cs-020) and [Part C for C#](../migration/part-c-csharp.md#cs-020-migration).
- **A settings object that sets the Relativity API user name and password pair is found in C#.** Two members whose names start with `Rsapi` and end in `UserName` (or `Username`) and `Password`, set in two assignments within five lines or in one object initializer, are reported at High, and at Medium in test code. **Declared limits:** a pair whose members are more than five lines apart or in different files, whose password is set before the user name, one half in an initializer and the other assigned separately, an initializer with a nested brace or more than 600 characters between the members, two names with different middle parts, the same extra prefix before `Rsapi` in both names, or a value that is a calculation is not reported. A declaration written over two lines can be reported as if it set the pair. Search for `Rsapi` and review each settings object by hand. See [Part A for C#](../migration/part-a-csharp.md#cs-017).
- **A credential stored in a member and handed to a mail, proxy or file-transfer client is a low-confidence finding, no longer a medium-confidence network credential.** When a network credential is stored in a member of a settings object, such as `settings.MailCredential`, and the same member is later handed to the mail client, the web proxy or a file-transfer request, the tool follows it and reports it at Low for manual review, as it already did for a credential written at the hand-over itself. Before, it was reported at Medium as an ordinary network credential, which was a false finding. **Declared limits:** the tool follows the credential only inside a window of 30 lines, across lines of at most 400 characters, with the client created after the credential is stored (or in the same statement, for the mail client and the proxy), and with no line in between that holds the word `NetworkCredential`. Outside that window, or when the client is held in a field or a parameter, when the member is written differently at the hand-over or copied through a variable first, or when the credential is created inside an initializer or held in a single variable, the credential is still reported at Medium and is a false finding if it goes to a mail, proxy or file-transfer server: confirm the destination of every such finding. A credential that the same file also hands to an HTTP client through that member may not be reported at the HTTP use, so review the HTTP use by hand. A client or a hand-over written inside a comment or a text can be taken for real code. See [Part A for C#](../migration/part-a-csharp.md#cs-019) and known issue 41.
- **For these three C# corrections the result changes in two ways.** Calls and settings objects that the earlier release did not report are now reported, and a credential that the earlier release reported at Medium, because it was stored in a member before being handed to a mail, proxy or file-transfer client, is now reported at Low. This is one more reason to assess a repository again, as said at the top of this section.
- **The time limit on the tool's matching is 112 seconds, raised from 110.75.** The slowest benign file measured over the six languages, on Windows and on a Linux virtual machine, took 11.18 seconds, and the limit was set again at ten times that figure, rounded up. A file that reaches the limit is still stopped, its findings are not reported, and the report counts it. See known issue 9.
- **What was measured for the changes of 0.6.1-alpha.** The changes of the list above, the Low reading of a colon-joined pair, the Low reading of a switched-off block and the Low report of a header read from a settings property, were measured on planted items that were written blind from the documented description of each change and frozen before the first change was written, and the earlier planted sets were measured again. In JavaScript and in TypeScript the header read from a settings property was reported at Low only, and none of the 19 near-misses planted for JavaScript and none of the 18 planted for TypeScript was reported by that class. The colon-joined pair in C# was then corrected a second time, to read an identifier word after a credential word, and measured on a new set of planted items that was written blind from the signed description and frozen before the correction was written. On that set, recall on the planted pairs at High or Medium was 35 of 36; 6 of 60 near-misses were reported at High or Medium, and all six are the form that is declared as remaining, a pair in which one half is named like a user or a secret and is not an identifier (see known issue 47); without that form, 0 of 54 near-misses were reported at High or Medium. The rate of 6 of 60 is at the ceiling of at most 10 %, so it meets it with no margin. After each of the two changes the earlier planted sets were measured again, and no genuine positive that counts toward recall was lost. **This is a bounded measurement too:** the planted items and the changes trace to one description, so the figures show that the tool reads the forms the description names and not that it reads every form of the kind in real code, and a genuine case that is now reported at Low, as described above, is counted as a miss and not as a success.
- **What was measured for the C# corrections of the previous list, and what it does not show.** The corrections were measured on a set of planted items that was planted blind from the signed description of the classes and frozen before the first correction was written. In that measurement, recall on the planted patterns at High or Medium was 38 of 38 (lower end of the 95 % Wilson interval 90.8 %), counted without the one class that is always routed to manual review and is judged separately; it is 38 of 58 when the 20 further planted positives that count toward neither figure are added. The recall was 18 of 18 for the `GetProxy` call and 14 of 14 for the `Rsapi` pair; 0 of 45 near-misses were reported at High or Medium; flow assignment was 38 of 38; and 19 of 19 near-misses of a credential stored in a member and handed to a mail, proxy or file-transfer client were reported at Low. The recommendation coverage of every High and Medium finding of the whole benchmark was 285 of 285. The earlier planted sets, 1,926 items in all, gave the same results as before the corrections. **This is a bounded measurement.** The planted items follow the same description the corrections were written from, so the figures show that the tool reads the forms the description names, not that it reads every form of the kind in real code. The forms it does not read are the declared limits above. See [What the figures cover](03-limits.md#what-the-figures-cover).

### Known issues added in 0.6.1-alpha

The known issues 1 to 41, listed under [Version 0.6.0-alpha](#version-060-alpha) below, still apply, except where an entry below says otherwise. These entries describe the behaviour of `0.6.1-alpha`, with detection catalog `1.45.1`.

42. **An `Authorization` header whose value is read from a settings property is reported at Low only in the form the tool was shown.** The header is written `headers: { Authorization: settings.serviceAuthorization }`, the file assigns a property of that name (a name that ends with `authorization`) from an environment variable whose name has a credential word in it (`auth`, `token`, `secret`, `credential`, `key`, `pass` or `basic`), and the finding is `JS-019`, at Low, with no flow and no recommendation. The property is joined by its name alone, so a name that is assigned twice in the file, a literal assignment of the same name and a class field of the same name with an initializer hide the use. A property under another name (`auth`, `authHeader`), bracket access, destructuring, optional chaining, an object shorthand, a call written as the receiver, several members written on one line, a class field assigned from an environment value, a property filled from a call, from an alias of the environment object or from another file, an environment variable named for a host, an address or a port, and a property whose fallback names a scheme are not reported. In TypeScript, a non-null mark or a cast after the property or after the environment read is not reported either. A site is also not reported when an explicit `Bearer` value for an `Authorization` header is written within thirty lines of it. Where the tool reports nothing and the header value comes from a settings object, search by hand; where it reports `JS-019`, open the site and check what the deployed value holds. See [Part A for JavaScript](../migration/part-a-javascript.md#js-019) and known issue 28.

43. **Two JavaScript and TypeScript forms are not detected, and the tool says so.** A user name and a password joined by a colon and given to the project's own encoder function, in a file that never names the Basic scheme, is not reported, because the tool recognizes only the standard encoders (`btoa` and `Buffer`) and a function of the project's own gives it nothing to anchor on: no scheme word, no header and no encoding it can see. A credential, options or header object that is chosen by a selector (an enumeration, a switch or a map) and returned from a function, with no client visible in the same statement, is not reported either, because the tool reads one expression at a time and does not follow a value from where it is chosen to where it is used. Both are declared as not covered in the catalogs of JavaScript and TypeScript and in Part A, and the tool offers no Low reading for them, since there is nothing in the text to report. A repository whose Basic Authentication is written in these forms can show fewer findings than it holds: search for the project's own encoding helpers, and for functions that return credentials or client options, by hand. See [Part A for JavaScript](../migration/part-a-javascript.md#declared-unsupported-coverage) and [Part A for TypeScript](../migration/part-a-typescript.md#declared-unsupported-coverage).

44. **A C# type from another library with the same name as the Relativity credential type is reported at High.** The tool recognizes the Relativity SDK credentials type by the name as it is written in the code, and not by the library the type comes from. A type of another library, or of your own, that has the same simple name and is built from a user name and a password is reported at High as `CS-001` although it is not a Relativity credential. Check the library of every `CS-001` finding before you migrate it, and dismiss the ones whose type does not come from the Relativity SDK. This release does not change it. See [Part A for C#](../migration/part-a-csharp.md#declared-unsupported-coverage).

45. **Some genuine C# findings are reported at Low, so they do not count among the findings you migrate first.** A colon-joined user name and password that is encoded to Base64 is reported at Low when neither half is named like a user name or a password, which includes two neutral names, names that use a credential word the tool does not list, and names that end in an identifier word such as `Id` or `Guid`. Code under a conditional-compilation symbol that only the project file or the build command defines is read as switched off and is reported at Low, although it is part of the build, and so is code under a build symbol outside the list of symbols the tool treats as supplied by a build. The report names the reason of each of these Low findings. A Low finding goes to manual review with no flow and no recommendation: read every one before you dismiss it. In the other direction, see known issue 47. See [Part A for C#](../migration/part-a-csharp.md#cs-009) and [Part A for C#, how confidence is assigned](../migration/part-a-csharp.md#how-confidence-is-assigned).

46. **VB.NET and PowerShell are read as before.** The two readings that this release changes for C#, a colon-joined pair at Low when neither half is named like a credential and a switched-off conditional-compilation block at Low, do not apply to them. A VB.NET block under a `#If` condition that is false is still read as code and reported at its ordinary level (see known issue 18), and a colon-joined pair in a VB.NET or a PowerShell file is read by its own rules, as described, for VB.NET, in known issues 20, 21 and 31 and in [Part A for VB.NET](../migration/part-a-vbnet.md), and, for PowerShell, in [Part A for PowerShell](../migration/part-a-powershell.md#ps-010).

47. **A colon-joined pair in C# with one half named like a user or a secret that is not an identifier is still reported at Medium.** A pair of two values joined by a colon and encoded to Base64 is reported at Medium when at least one half is named like a user or a secret and that name is not directly followed by an identifier word (`Id`, `Ids`, `Identifier`, `Guid`, `Uuid`, `Number`, `Index` or `Code`). A pair of an account name next to a region name, or of a login next to a tenant name, has such a half, so it is reported at Medium with a recommendation although it is not a credential. In the measurement of this correction, all 6 of the 60 planted near-misses that were reported at High or Medium were of this form. Check the two halves of every Medium finding of this class before you migrate it, and dismiss the pair that is not a credential. See [Part A for C#](../migration/part-a-csharp.md#cs-009).

## Version 0.6.0-alpha

This is an **alpha** release. It is the eighth build of the first version of the tool: it adds TypeScript to C#, PowerShell, VB.NET, Shell and JavaScript, corrects the way several of those languages are read, scans a `bin` folder that holds scripts and no project file, raises the time limit on the tool's matching, and has the known issues listed below. The version string is `0.6.0-alpha`. The tool prints it with `--version`, in the session banner, and in the provenance of the report and of the JSON data file, beside the version of the detection catalog (`1.43.0` in this release).

Use an alpha release to assess repositories and to give feedback. Read every finding and recommendation before you act on it: the tool locates Basic Authentication and proposes a migration, and you decide.

### Changes from 0.5.0-alpha

The changes that `0.5.1-alpha` made, listed under that version below, are part of this release too. The changes since `0.5.1-alpha` are these.

- **TypeScript is analyzed.** The tool analyzes TypeScript files: files ending in `.ts`, `.tsx`, `.mts` or `.cts`, and declaration files (`.d.ts`, `.d.mts` and `.d.cts`), which it reads and reports at Low. It has twenty pattern classes, each described in [Part A of the Migration Documentation for TypeScript](../migration/part-a-typescript.md), with the constructs the catalog declares unsupported. Eighteen are the classes of JavaScript, read on TypeScript files, and a finding in a `.ts` file shows the same identifier, from `JS-001` to `JS-018`, with TypeScript as its language; two exist for TypeScript alone, `TS-001` (a typed credential object, Medium) and `TS-003` (an injected NestJS HTTP service, High). Six of the classes, `JS-007`, `JS-009`, `JS-011`, `JS-014`, `JS-016` and `JS-018`, are always Low and always go to manual review. The migration suggestion for each class and each flow is in [Part C for TypeScript](../migration/part-c-typescript.md). **A repository whose TypeScript files were counted and not analyzed in an earlier release can now report TypeScript findings.** TypeScript written inside other files, such as single-file components, HTML templates, notebooks and Markdown documents, is not read, and neither is a script with no extension whose first line names `ts-node`, `tsx` or `deno`; search those by hand with the searches in Part A. **A clean TypeScript result does not cover them, and it does not cover a credential that lives in a `.env` file or in another configuration file.**
- **The recommendations for TypeScript name the kind of application they are for.** The tool does not know whether a file runs in a browser, in a Node.js server or in a command-line tool, so the Authorization Code recommendation has a variant for a browser (an Angular application, for example), a Node.js server (a NestJS server, for example) and a Node.js command line, and the Client Credentials recommendation has a variant for a Node.js process and one for browser code that does not act for a signed-in user. Each variant opens with the condition it is for; keep the one that describes your code. A browser never holds the client secret or a token, and a credential written into browser code has been public for as long as the code has shipped, so the recommendation says to treat it as compromised and to rotate it. See [Part C for TypeScript](../migration/part-c-typescript.md#choosing-the-variant-for-your-application).
- **Test code in TypeScript is reported as in the other languages.** Medium is the ceiling for test code: a construct that is reported at High elsewhere is reported at Medium when it sits in test code. A mock, a sample, vendored code, a generated file or a declaration file stays Low, and so does a file that is test code and also one of those. Part A lists the signals for [TypeScript](../migration/part-a-typescript.md#how-confidence-is-assigned).
- **A new Low class reports an `Authorization` header whose whole value is read from the environment.** For JavaScript and for TypeScript, a header written as `headers: { Authorization: process.env.<NAME> }` (or with `import.meta.env`, `Deno.env.get` or `Bun.env`), alone, with a `||` or `??` fallback, or with the value first copied into a variable in the same file, is reported as `JS-018` at Low for manual review, with no flow and no recommendation: the scheme is inside the variable, and the tool cannot tell from the code whether it is Basic. A fallback literal that begins with `Basic` is a Basic header written in the code itself and is reported at High; a site is not reported when an explicit `Bearer` value for an `Authorization` header is written within thirty lines of it. Before, such a header was not reported at all. See [Part A for JavaScript](../migration/part-a-javascript.md#js-018) and known issue 28.
- **An address with credentials held under a proxy name is no longer reported as a credential for the service.** In JavaScript and in TypeScript, a name or a key that contains `proxy` or `proxies`, in any letter case, marks an address with a user name and a password as a credential for a proxy, and the tool does not report it. Before, such an address was reported at Medium. A name of this kind that holds an address for the service itself is not reported either, so review such names by hand.
- **A credential is a literal only when it is the whole value.** In JavaScript and in TypeScript, a password or a token written as a literal that is concatenated with code, or that is followed by a TypeScript cast, a `satisfies` clause or a non-null mark, no longer raises the warning that a credential is written into the source. Before, a literal joined to code was counted as a literal credential. The class and the level of the finding do not change.
- **A C# credential-cache entry with a port is read whatever the port is.** The four-argument `Add` that takes a host, a port, the scheme and a constructed credential is reported as `CS-003` when the port is any single argument written on one line: an integer in decimal, hexadecimal or with digit separators, a named constant, a cast, a call or a short expression. Before, an entry whose port was written in some of these forms could be missed. See [Part A for C#](../migration/part-a-csharp.md#cs-003).
- **A C# mail client or proxy created with an initializer is no longer reported as a plain credential.** `new SmtpClient(host, port) { EnableSsl = true };` followed within five lines by `.Credentials = new NetworkCredential(user, password)` is now reported at Low as a credential for a client that is not an HTTP client (`CS-019`), as the same client without the initializer already was. Before, the credential was reported at Medium as a plain credential construction. See [Part A for C#](../migration/part-a-csharp.md#cs-019).
- **A C# credential built inside a credential-cache entry under a scheme other than Basic is no longer reported.** `cache.Add("<host>", 8080, "Digest", new NetworkCredential(user, password))` is not a Basic entry, and the credential inside it is no longer reported as a plain credential construction at Medium. An entry under `Basic` is still reported as `CS-003`, and a credential held in a variable and given to the cache is not affected. For a scheme written as an identifier, see known issue 32.
- **A Shell array of command options can be much longer.** An array whose credential option stands far into its text, on one line of up to 10,000 characters or across up to thirty lines of at most 400 characters, is reported as `SH-009`. Before, an array whose text was longer than a few hundred characters could be missed. A longer array is still not read. See [Part A for Shell](../migration/part-a-shell.md#sh-009).
- **A Shell here-document opened inside a one-line backtick substitution has no body.** As in `bash` and `dash`, the lines after the substitution are commands, so a credential on one of them is reported at its own level and no longer at Low. The same holds for a here-document opened inside a `$( )` that stands in the body of an unquoted here-document. See [Part A for Shell](../migration/part-a-shell.md#how-confidence-is-assigned).
- **The Shell pages say how far the Basic-challenge statement can be trusted.** The Low findings for a client that sends Basic only after the server challenges with Basic say that RelativityOne does not challenge with Basic, and that this rests on a single RelativityOne instance, is not documented by Relativity, and was not probed on Relativity Server. A call that points at another server is still yours to confirm.
- **A Base64 pair that is a literal followed by a concatenation is now read.** In JavaScript and in TypeScript, `'Basic ' + btoa('exampleUser:exampleSecret' + suffix)`, a quoted literal pair that continues into a concatenation inside the encoder call, is reported as `JS-005` at Medium. Before, the pair was not read when it was followed by a concatenation. A pair that is the whole argument of the encoder is read as before. See [Part A for JavaScript](../migration/part-a-javascript.md#js-005).
- **A pair split across two literals is read, and a member written as a bare name is read.** In JavaScript and in TypeScript, `'Basic ' + btoa('exampleUser:' + 'exampleSecret')`, a literal whose last character is the colon followed by a plus and a second quoted literal, is reported as `JS-005` at Medium and raises no warning that a credential is written into the source, because no one literal holds the pair. A literal that ends in a colon followed by code (`btoa('exampleUser:' + secret)`) is still not read; see known issue 30. A member of the `auth` option of an `axios` or `request` call that is written as a bare name, `{ username, password }` or `{ username: accountName, password }`, is now read as `JS-001` at High. Before, only a member written with a key and a colon was read. See [Part A for JavaScript](../migration/part-a-javascript.md#js-001).
- **The typed credential object of TypeScript is read whatever its values are, and the injected-service class reads two member names.** `TS-001` reads the `username` and `password` members of the object whatever follows the colon (a name, a member access such as `this.clientSecret`, a call, a template or a literal) and a member written as a bare name, so an object that was reported at Low as `JS-011` is now reported at Medium as `TS-001`. The warning that a credential is written into the source is still raised only when the password is a whole literal. `TS-003` reads only the members `username` and `password`, also written as bare names; an object with the members `user` and `pass`, which `TS-003` read at High, is now left to the Low reading of a plain `auth` object (`JS-011`). See [Part A for TypeScript](../migration/part-a-typescript.md#ts-001).
- **A `bin` folder that holds scripts and no project file is scanned.** The scan skips a folder named `bin` only when a project file (`.csproj`, `.vbproj` or `.fsproj`) sits beside it, because that is where a build leaves its output. A `bin` folder with no project file beside it is read like any other folder, so a script kept there is now assessed, and build output beside a project file stays excluded. Before, every folder named `bin` was skipped. The other seven folder names are still skipped. See [What the scan reads and what it leaves out](01-using-the-tool.md#what-the-scan-reads-and-what-it-leaves-out).
- **The time limit on the tool's matching is 110.75 seconds, raised from 44.25.** The slowest files measured, TypeScript files with many typed header writes close together, need more time than the files of the other languages do, and the limit was set again from the slowest case measured over the six languages, on Windows and on a Linux virtual machine. A file that reaches the limit is still stopped, its findings are not reported, and the report counts it. See known issue 9.
- **The console names the output folder as you wrote it.** The line the tool prints for each file it writes, `Written: <file name> (in the output folder <folder>).`, and the message for an output folder that cannot be written to now show the folder as you gave it, on the command line or in the configuration file, and relative to the folder you started the tool from when you gave none or a relative path, for example `./Outputs`. The full resolved path is never printed. The Markdown report and the JSON data file still do not name the output folder.
- **A leading `~` in `outputPath` is expanded.** In the configuration file in your user profile folder, an `outputPath` that starts with `~`, `~/` or `~\` now means your home folder. Before, the text was read as a folder named `~` inside the folder you started the tool from. If the tool cannot determine your home folder, or the path names the home folder of another user (`~name`), it says so and does not start the session, with exit code 4. A value given with `--documentationDestinationFolderPath` is not changed by the tool, because your shell expands a `~` you type, and `--repositoryFolderPath` is not expanded. The expansion was tested on Windows and on Linux and has not been measured on macOS. See [The configuration file](01-using-the-tool.md#the-configuration-file).
- **A session saved by `0.5.1-alpha` is not resumed.** The detection catalog moves to version `1.43.0`, and a session saved under another catalog version is started fresh. See known issue 6.

### What this release supports

- **Languages: C#, PowerShell, VB.NET, Shell, JavaScript and TypeScript.** The tool analyzes C# source files (`.cs`), PowerShell files (`.ps1`, `.psm1` and `.psd1` files, and files without an extension whose first line names the PowerShell interpreter), VB.NET source files (`.vb`, including the code-behind of a web page, which ends in `.aspx.vb`) Shell scripts (`.sh`, `.bash`, `.zsh` and `.ksh` files, and files without an extension whose first line names `bash`, `sh`, `zsh` or `ksh`), JavaScript files (`.js`, `.mjs`, `.cjs` and `.jsx` files, and files without an extension whose first line names `node` or `nodejs`) and TypeScript files (`.ts`, `.tsx`, `.mts` and `.cts` files, and declaration files, which are reported at Low). Scripts for `fish`, `csh` and `tcsh`, Windows batch files (`.bat`, `.cmd`), shell start-up files (`.bashrc`, `.profile`, `.zshrc` and the like), `.bats` test files, a script with no file extension whose first line does not name `bash`, `sh`, `zsh` or `ksh`, in lower case, as the interpreter, directly or after `env` and any options written as one word, such as `dash`, `ash`, `mksh`, `ksh93` or `busybox sh`, or that puts a separate argument word or a variable assignment between `env` and the shell (the first line is read only for a file with no extension: a file ending in `.sh`, `.bash`, `.zsh` or `.ksh` is read whatever its first line names, and a file with any other extension is not attributed to Shell by its first line), and shell commands written inside other files (CI pipeline definitions, Dockerfiles, Makefiles, crontabs, service unit files, Markdown documents) are not analyzed as Shell. Files in any other language, including Python and Go, are counted in the scan summary and are **not analyzed in this release. An empty result for those languages does not mean that no Basic Authentication was found.** A finding in a language that is not yet delivered, Python or Go, is not reported.

- **Measured accuracy.** The detection, flow-assignment and recommendation-coverage figures measured for C#, for PowerShell and for VB.NET, with what they do and do not show, are in [What the figures cover](03-limits.md#what-the-figures-cover). For VB.NET, over its full benchmark: recall on the patterns the catalog covers is **98.4 %** (242 of 246), and **88.1 %** (252 of 286) when the planted patterns the catalog declares it does not cover are counted as well; the false-positive rate on near-misses is **9.4 %** (13 of 139), against a target of at most 10 %; flow assignment is 242 of 242 and recommendation coverage is 280 of 280. On the independent part of that benchmark, recall is **95.1 %** (58 of 61), **87.9 %** (58 of 66) with the declared patterns counted, and the false-positive rate is **20.0 %** (11 of 55), which is above the target. See known issue 19. The VB.NET figures were measured for `0.3.0-alpha`, before the VB.NET corrections made in `0.4.0-alpha`. **No accuracy figure is stated for Shell, for JavaScript or for TypeScript in this release.**
- **Both OAuth 2.0 flows.** Every High or Medium finding, in any of the six languages, is given a recommended flow, Client Credentials or Authorization Code, with a note that asks you to confirm the choice, and a migration recommendation for that flow. The recommendations are the ones in [Part C for C#](../migration/part-c-csharp.md), [Part C for PowerShell](../migration/part-c-powershell.md), [Part C for VB.NET](../migration/part-c-vbnet.md), [Part C for Shell](../migration/part-c-shell.md), [Part C for JavaScript](../migration/part-c-javascript.md) and [Part C for TypeScript](../migration/part-c-typescript.md). ### Installing and running

The steps are in [Using the tool](01-using-the-tool.md): download the file for your platform and `SHA256SUMS`, [verify the checksum](01-using-the-tool.md#verifying-the-checksum), follow the [first-run steps](01-using-the-tool.md#first-run) for your platform (the Windows and macOS binaries are unsigned, so Windows SmartScreen asks you to confirm and macOS Gatekeeper asks you to allow the file), and start a session:

```text
migrate-auth --repositoryFolderPath <path to the repository> --documentationDestinationFolderPath <path to an output folder>
```

At the prompt run `scan`, `analyze`, `suggest` and `report` in that order.

### Known issues

The items below affect how the tool behaves or what its text says in this release.

1. **The Authorization Code endpoints are verified by NSerio and not documented by Relativity.** The authorize endpoint and the code exchange that the Authorization Code recommendations use were verified by NSerio against a live RelativityOne instance. Relativity does not document them, and its own confirmation is pending. The recommendations label them "verified by NSerio against a live instance; not documented by Relativity". PKCE is required by Relativity's documentation to obtain a refresh token; the `S256` method is NSerio's recommendation, because Relativity does not document which method it accepts.

2. **Relativity has not stated a recommendation for distributed desktop applications.** A desktop or command-line application that uses Authorization Code has to embed a client secret, and a secret shipped inside a distributed binary can be extracted by anyone who holds the binary. The desktop guidance in the recommendations is NSerio's guidance, verified to work; it is not a Relativity recommendation. Confirm it against your own security policy. The PowerShell recommendation for a desktop script, and the Node.js command-line variant of the JavaScript and TypeScript recommendations, follow the same guidance.

3. **The Windows and macOS binaries are unsigned.** Windows SmartScreen shows a warning the first time you run a downloaded copy. The macOS binaries are not signed with an Apple Developer ID certificate and not notarized by Apple, so macOS cannot vouch for them: Gatekeeper blocks the first run of a copy downloaded with a web browser until you allow it, and the checksum is the only check that your download is intact. The first-run steps for [Windows](01-using-the-tool.md#first-run-on-windows) and for [macOS](01-using-the-tool.md#first-run-on-macos) explain how to continue after you have verified the checksum. Signed, notarized macOS disk images are planned for a later release.

4. **There is no automated build and release pipeline yet (continuous integration and delivery is deferred).** The binaries of a release are built by hand. The release publishes a `SHA256SUMS` file. Verify the checksum of every download.

5. **The first launch of a freshly downloaded copy can take longer than one second.** In the measurement made for an earlier release, the first launch of one freshly downloaded copy on Windows took 4.874 seconds; two other freshly downloaded copies, and three copies that were not marked as downloaded, started in about 0.17 seconds, and every second launch took about 0.03 seconds. The cause was not measured. The first launch on macOS has not been measured yet. There is no first-launch figure for Linux, because Linux does not run a reputation check on a downloaded binary.

6. **A session saved by another build is not resumed, and this includes every session saved by an earlier release.** The saved state of a session is resumed only when its state format version and its detection catalog version are both equal to those of the running tool. The state format of `0.6.0-alpha` and of `0.6.1-alpha` is session schema 9, the same as in `0.4.0-alpha`. The detection catalog is version `1.43.0` in `0.6.0-alpha` and `1.45.1` in `0.6.1-alpha`, and the earlier releases, `0.1.0-alpha`, `0.1.1-alpha`, `0.2.0-alpha`, `0.3.0-alpha`, `0.4.0-alpha`, `0.5.0-alpha` and `0.5.1-alpha`, used other catalog versions, so a session saved by any of them is not resumed, and a session saved by `0.6.0-alpha` is not resumed by `0.6.1-alpha`. The tool says so, does not use it, and starts a fresh session: run `scan` again. The same happens with a state written by a newer build. The tool version itself is not compared, so two builds with the same versions of both can resume each other's sessions.

7. **File names in decomposed Unicode form are identified less strictly.** Two file names that differ only in their Unicode normalization form are reported as two files, and a file name in decomposed form (as macOS returns some names, and as a name can be on Windows NTFS or on a Linux file system, which keeps names byte for byte) may be positioned and identified differently from the same repository scanned on another platform. Detection within each file is not affected. On a repository that reaches the limit of 50,000 findings for one scan, the findings kept are the first ones in path order, and that order depends on the normalization form, so the findings kept can differ between platforms. See [Limits of the tool](03-limits.md#file-names-in-decomposed-unicode-form).

8. **The flow is chosen from signals in the finding's own file, one file at a time.** In real code the credential often reaches that file from another one, so most findings take the default flow with a note asking who supplies the credential. This holds for C#, for PowerShell, for VB.NET, for Shell, for JavaScript and for TypeScript. In a PowerShell script that reads a stored credential and falls back to a prompt for one when none is stored, both signals are in one file and the tool resolves that file to Authorization Code; see [Limits of the tool](03-limits.md#a-script-with-both-a-stored-credential-and-a-prompt). A Shell script that reads a credential from the environment and falls back to `read -s` is resolved in the same way, and so is a JavaScript file that reads a credential from `process.env` and falls back to a hidden prompt. For VB.NET, see known issues 15 and 16, and for TypeScript, known issue 39. Pointing to interactive-user evidence found elsewhere in the same repository is planned after the alpha.

9. **The time limits on the tool's matching are provisional.** The tool bounds the time it spends evaluating each of its own search expressions on a file, currently 112 seconds, and the time it spends on the first-line check of a file and on reading the strings and comments of a file, currently 1000 milliseconds for each. The 112-second limit and this one were each chosen with a tenfold margin over the slowest benign case measured on Windows and on a Linux virtual machine, and neither has been confirmed on macOS or on other hardware. What the user sees when a limit is reached depends on which one:
   - **The 112-second limit.** The tool stops analyzing the file and discards **every** finding for that file, and the report counts the file under "Files whose analysis took too long and was stopped; their findings are not reported". Review such a file by hand.
   - **The 1000-millisecond limit on the first-line check, during `scan`.** The tool does not use the first line to recognize the file's language. It identifies the file by its extension instead; a file without an extension then counts as a file whose language was not recognized, so a PowerShell, Shell or JavaScript script that has no extension is not analyzed. The report says how many files were identified by their extension for this reason ("Files attributed by extension because first-line detection exceeded its budget"), and the JSON data file carries the count as `firstLineFallbackFiles`.
   - **The 1000-millisecond limit on reading strings and comments, during `analyze`.** The tool stops reading the file as code at the point where the limit was reached, keeps the findings before that point, and reports **no** finding at or after it. The report counts the file under "Files only partly readable as code, so not analyzed in full". Review the rest of that file by hand. In a Shell script the limit also covers the read-ahead for arithmetic.

10. **A file in a single-byte code page other than Windows-1252 can be read with the wrong characters.** The tool reads a source file as UTF-8, UTF-16 or UTF-32 when it starts with a byte order mark, and as UTF-8 or UTF-16 when it does not. A file that is none of these is read as Windows-1252, which covers Latin-1 and the other Western European files; the report counts such files and names them under "Files read as Windows-1252" (`scanSummary.legacyEncodedFiles` in the JSON file). The tool cannot tell which single-byte code page a file was written in. A file in another one, for example a Cyrillic or Central European code page, is read with its accented or other non-ASCII characters changed, or, when it holds a byte that Windows-1252 leaves undefined, is counted under "Files that could not be read as text" and is not analyzed. A credential written in plain ASCII is found either way; one whose value holds a non-ASCII character is read with the wrong character. A UTF-8 file with a damaged byte sequence is also read as Windows-1252. This applies to C# files, PowerShell scripts, VB.NET files, Shell scripts, JavaScript files and TypeScript files alike. Convert such files to UTF-8 and scan again, or review them by hand.

11. **One construct can be reported as two findings at the same place in C#, PowerShell, VB.NET, JavaScript and TypeScript.** A Basic `Authorization` header built from a user name and a password that are encoded where the header is written is reported once as the header (`CS-005`, or `CS-006` when the header name is written as a string) and once as the encoded pair (`CS-009`), on the same line or a few lines apart. Both findings belong to one migration, and both locations need to be fixed together. This is not the case for a credential cache entry, which is one finding, nor for an authentication helper (`CS-011`): the helper's definition is one finding and the credential it builds, when the tool recognizes it, is another, at its own line. A PowerShell header built the same way is reported as the encoded pair (`PS-010`) and the header write (`PS-005`), at two locations that need the same attention. In Shell the tool reports one finding for each command, the most specific one, so a `curl` call with both `-u` and an address with a password, or a header whose token is built in a substitution, is one finding; a command that a backtick substitution or a subshell in parentheses splits, and a `>&3` or `&>` redirection, which the tool reads as a command separator, can still give two findings for one command. In JavaScript, and in TypeScript, which is read with the same rules, an encoder written inside a Basic header write is read as part of the header finding, but an encoder in one statement and the header that uses it in another are reported as two findings, the encoder's finding being the expected one of the pair, and so are the two assignments of the user name and the password of a `URL` object.

12. **For the legacy Import API construction (class `CS-015`), no documented factory accepts a token that a standalone or desktop process acquired itself.** The recommendation for this class names the one documented factory, `ImportAPI.CreateByRsaBearerToken(webServiceUrl)`. It takes no token, and Relativity documents it for processes hosted by the Relativity service account, for example an agent. Relativity's Import API concepts page lists bearer-token authentication as not supported for a desktop application. The recommendation therefore gives no code form for a standalone or desktop process that would obtain an OAuth2 token itself, and says so. Both pages are Relativity Server documentation, and no RelativityOne page for this legacy class was found, so whether the factory exists in an SDK version aimed at RelativityOne is not established. The sources are [`ImportAPI.CreateByRsaBearerToken`](https://platform.relativity.com/Server2021/Subsystems/importapi/Content/html/M_kCura_Relativity_ImportAPI_ImportAPI_CreateByRsaBearerToken.htm) and [Import API concepts](https://platform.relativity.com/Server2025/Content/Import_API/Overview/Import_API_concepts.htm). The entry for this class in [Part C](../migration/part-c-csharp.md#cs-015-migration) says the same.

13. **The recommendations were run only against a local test server, not against RelativityOne.** The scripts in the PowerShell migration suggestions that acquire a token and call the API were run on Windows PowerShell 5.1 and on PowerShell 7 against a local server that imitates the token endpoints and the API of RelativityOne. They were not run against a RelativityOne instance. Every statement the scripts make about how RelativityOne behaves rests on Relativity's documentation and on NSerio's earlier verification, not on this run, so the local run shows that the scripts work as written and not that RelativityOne accepts them. Try each script against a test instance before you rely on it. The VB.NET recommendations were compiled, and the token-acquisition code in them was run against the same kind of local server and not against RelativityOne. The C# recommendations were not run against RelativityOne either, and neither were the Shell recommendations. The Shell token-acquisition scripts were run against the same kind of local server, in `bash` and `dash` on Windows and in `bash`, `dash`, `zsh`, `ksh` and `mksh` on Linux, and not on macOS; `jq`, which they use to read the token from the response, was installed on neither system: the run put a stand-in for the one filter the scripts use, `jq -r '.access_token'`, on the path, so that filter ran against the stand-in and not against `jq`. The JavaScript recommendations were checked in a narrower way: Node.js read every code block for syntax (`node --check`), and the token-acquisition blocks of a Node.js process, a Node.js server and a Node.js command line were run against a local server on one version of Node.js. The blocks send no scope and the local server requires one, so a small shim added a `scope` field to the token request; the text says that no single scope is required, and you must use the value the API documents. The sign-in redirect was played by the test program and not by a browser, and the browser variants were not run in a browser. Nothing was run against RelativityOne, so the check shows that the blocks read and run against that local server, not that RelativityOne accepts them. Try each block against a test instance before you rely on it. The TypeScript recommendations were checked in the same narrower way. The token-acquisition blocks that Node.js can run by removing the types, those of a Node.js process, a Node.js server and a Node.js command line, were run against the same kind of local server, on Windows and on a Linux virtual machine; the local server required a scope that the blocks do not send, so a small addition supplied one for the run, and you must use the scope value the API documents. The Angular and NestJS shells were only compiled, against stand-in declarations of the framework packages and not against the packages themselves, and the browser block was compiled as a `.tsx` file and was not run in a browser. Nothing was run against RelativityOne, so try each block against a test instance before you rely on it. `curl` and `jq` must be installed where you run a Shell recommendation, and you should try the script with your own `jq` first. The desktop script, which opens a local listener to receive the sign-in redirect, was run from a process that was not elevated, under an account that is a local administrator; it has not been tried under a standard user account.

14. **In PowerShell, a password written as a quoted literal through `ConvertTo-SecureString` with `-AsPlainText` does not raise the literal-credential warning.** When such a secure string is wrapped in a credential object and passed to `-Credential`, the finding is reported at its level with no warning that a credential is written in the script. A literal written straight into `New-Object System.Net.NetworkCredential(...)` or into a Basic `Authorization` header does raise it. If you use the warning to find the secrets to rotate, search the PowerShell files by hand for `ConvertTo-SecureString` used with `-AsPlainText`. See [Limits of the tool](03-limits.md#the-literal-credential-warning-is-read-from-where-the-credential-sits) and [Part A for PowerShell](../migration/part-a-powershell.md#declared-unsupported-coverage).

15. **A VB.NET file whose flow evidence is in another file takes the default flow, and a Web Forms page is read by its code-behind alone.** A page whose login control is declared in the `.aspx` markup and whose code is in the `.aspx.vb` file is decided by the code-behind; the markup is not scanned. If the code-behind holds no login handler of its own, its findings get the default flow, Client Credentials, with the note that asks who supplies the credential, although the page acts for a signed-in user. The same happens to any VB.NET file whose sign-in evidence is in a partial class, a module or a project the file does not contain. For code that serves a signed-in user, use Authorization Code whatever the tool recommended. See [Limits of the tool](03-limits.md#vbnet-web-forms-pages-and-a-file-with-both-kinds-of-evidence) and [Part C for VB.NET](../migration/part-c-vbnet.md#confirming-the-flow).

16. **A VB.NET file that holds both kinds of flow evidence receives Authorization Code.** When one file holds evidence that a person supplies the credential (a console prompt for a password, a password control, a login handler) and evidence that it is fixed (a credential-named setting, an environment variable or a secret-store read), the interactive evidence wins and the file's findings get Authorization Code. This includes a file that merely holds two unrelated pieces of code, one for a signed-in user and one that runs unattended. If the match is in the unattended part, use Client Credentials. See [Limits of the tool](03-limits.md#vbnet-web-forms-pages-and-a-file-with-both-kinds-of-evidence).

17. **A double quote the tool does not see closed makes it read the rest of a VB.NET file as text.** A stray or odd double quote, for example inside an XML literal, makes the tool read everything after it as the inside of a string, so every match after that point is reported at Low, with no flow and no recommendation. XML literals are not read at all. If a VB.NET file reports Low findings below some line where you expect higher ones, look for an unbalanced double quote above that line and review the rest of the file by hand. See [Limits of the tool](03-limits.md#vbnet-how-the-tool-reads-quotes-and-conditional-blocks).

18. **A VB.NET block switched off with a `#If` condition is read as code.** The tool does not evaluate conditional compilation, so a construct in a branch that is never compiled is reported at its ordinary level, and a double quote in it can end the analysis of the rest of the file as described in item 17. Check whether the branch is built before you migrate a finding in it.

19. **The tool reports some VB.NET code that is not Basic Authentication towards RelativityOne.** The false-positive rate on the independent part of the VB.NET benchmark measured for `0.3.0-alpha` is 20.0 % (11 of 55), against a target of at most 10 %; it is 9.4 % (13 of 139) over the full benchmark, where the corrected, older part lowers it. Most of the reported look-alikes are costs the catalog declares: a credential given to a share or mail consumer the tool does not list, a bearer value held in a variable whose name carries `token`, a host joined to a value that is not a port, and a name declared in two procedures. A system token given as the second argument of the Import API constructor, written as a call whose own argument holds a further call (`FetchPlatformToken(Resolve(scope))`), is still reported as a user-and-password pair, and so is a type of your own with the Import API type's name when it is declared in another file or farther than about one thousand characters from the use. Read every VB.NET finding at Medium before you act on it, and dismiss the ones that are not Basic Authentication towards RelativityOne. See [Limits of the tool](03-limits.md#vbnet-findings-that-are-not-basic-authentication).

20. **A few VB.NET forms of an encoded pair and of a header are not reported.** A user name and password joined by a colon and encoded are not reported as an encoded pair when the second half is held under a name that carries no credential word, such as `pin` or `passphrase`; a header value that names the scheme next to the conversion is still reported. An `Authorization` header whose value is held in a variable whose name carries `pass`, `pwd` or `apikey` in lower case followed directly by a digit, such as `pass2`, is not reported, while the same name with a capital first letter, `Pass2`, is. Search for these forms by hand with the searches in [Part A for VB.NET](../migration/part-a-vbnet.md). See [Limits of the tool](03-limits.md#vbnet-findings-that-are-not-basic-authentication).

21. **Some VB.NET encoded pairs are reported though they are a name and a size or a port.** The check that declines a half ending in `Length`, `Count`, `Size` or `Port` is not applied in every spelling of the pair: it is not applied to a first half ending in `Length`, `Count` or `Size` joined with `&` or `+`, to a half followed by `.ToString()`, to a second half ending in `Port` written inside the encoder call, or to a second half ending in `Length`, `Count` or `Size` written inside the encoder call with `&`, `+`, an interpolated string or `String.Concat`. In those spellings a name and a size or a port can be reported as an encoded pair when the second half carries a credential word. Read every VB.NET finding of an encoded pair before you act on it. See [Limits of the tool](03-limits.md#vbnet-findings-that-are-not-basic-authentication).

22. **Shell files that are not read, and shell code that lives in other files.** The tool does not analyze `fish`, `csh` or `tcsh` scripts, Windows batch files, `.bats` files, shell start-up files such as `.bashrc` and `.profile`, a script with no file extension whose first line does not name `bash`, `sh`, `zsh` or `ksh`, in lower case, as the interpreter, directly or after `env` and any options written as one word, such as `dash`, `ash`, `mksh`, `ksh93` or `busybox sh`, or that puts a separate argument word or a variable assignment between `env` and the shell (the first line is read only for a file with no extension: a file ending in `.sh`, `.bash`, `.zsh` or `.ksh` is read whatever its first line names, and a file with any other extension is not attributed to Shell by its first line), or shell commands written inside CI pipeline definitions, Dockerfiles, Makefiles, crontabs, service unit files and Markdown documents. In practice many command lines that pass a user name and password to an HTTP client live in those files, so a Shell result with no findings does not cover them. Search them by hand with the searches in [Part A for Shell](../migration/part-a-shell.md). See [Limits of the tool](03-limits.md#shell-what-the-tool-reads-and-what-it-does-not).

23. **A Shell credential in a file the script only reads is not reported, and neither is code that is never sent.** The contents of a `.netrc`, a `.curlrc`, a `.wgetrc` or an `.env` file, and any credential file the script reads and does not write, are not in the text the tool analyzes, and that is where a credential usually lives; search such files by hand. A credential the script writes into a configuration file itself is read. A construct that is built into a variable, an array or a pair and that no call uses within the next thirty lines is not reported, and an encoder whose output is printed or discarded is not read. Code in a dead branch or after an `exit`, and a function that is never called, is still reported as if it ran, because the tool does not parse the script. See [Part A for Shell](../migration/part-a-shell.md#declared-unsupported-coverage).

24. **Shell code that runs from a string is read only in the forms the tool lists.** A command inside `eval`, `bash -c` and the other shells with `-c`, `su -c`, `ssh host "..."`, a backtick or `${...}` in a double-quoted string, or a here-document fed to a shell is read as code. A command in another form is read as text and reported at Low, with no recommendation: the stage after a pipe on a continuation line, a script written to a file and run by a separate command, `bash < file`, process substitution, a here-string, a shell behind a prefix wrapper such as `env`, `nohup` or `exec`, a quoted command word, `$'...'`, and a string nested more than eight levels. A Low match inside a quoted command may be live code. See [Part A for Shell](../migration/part-a-shell.md#shell-run-from-a-string).

25. **A Shell script is read the way `bash` reads it, and `dash` and older `bash` read four forms differently.** The tool follows one family of shells. A here-document terminator written with ANSI-C quoting, a terminator continued across a backslash and a line feed, a terminator word quoted across a line feed, and a here-document opened inside a command substitution that closes on the opening line mean something else in `dash`, and the last also in `bash` before 5.2. In those forms the tool reads the lines after the here-document as its body where the shell runs them as commands, so a command there can be missed, and findings after them can be read at the wrong level. A script that names no dialect on its first line is read as `bash`. See [Part A for Shell](../migration/part-a-shell.md#declared-unsupported-coverage).

26. **Two limits of the Shell reader are silent.** More than 5,000 here-document openings waiting for their bodies in one region of a file, and an arithmetic double parenthesis whose closing is hidden by a here-document body or is past the per-file read-ahead budget, are read without any message: the opening stays code, and the run is read as not arithmetic. No ordinary script holds these, and a file in which they occur can be read at the wrong level after them. See [Part A for Shell](../migration/part-a-shell.md#declared-unsupported-coverage).

27. **A Shell mock or test with a neutral name is not recognized as one.** A test script is recognized by its folder, its file name or a test-library marker, and a mock, fake or stub by its folder or file name and by nothing else. A mock with a neutral name is reported at the level of its class, which can be High, and may be a false positive; a test with a neutral name outside every test folder is reported as production code. A folder named `Deployment` does not lower a Shell finding. See [Part A for Shell](../migration/part-a-shell.md#how-confidence-is-assigned).

28. **An `Authorization` header whose value is read from an environment variable is reported at Low for review, and the forms the tool does not read need a search of your own.** This is a limit of what the code shows and not a miss: the scheme is inside the variable, so the tool cannot tell from the code whether it is Basic, and it reports the site so that you see it. For JavaScript and for TypeScript, a header written as `headers: { Authorization: process.env.<NAME> }` (or with `import.meta.env`, `Deno.env.get` or `Bun.env`), alone, with a `||` or `??` fallback, or with the value first copied into a variable in the same file, is reported as `JS-018` at Low, with no flow and no recommendation. A fallback literal that begins with `Basic` is a Basic header written in the code itself and is reported at High; a fallback that begins with `Bearer` is not reported. A site is not reported when an explicit `Bearer` value for an `Authorization` header is written within thirty lines of it, before or after; the tool reads text and not code there, so a comment or a string that spells the header with a `Bearer` literal also hides the site, and so does a `Bearer` fallback of any environment read in the window. These forms are not reported at all: a chain of fallbacks, a read with optional chaining, a read held through another variable, a destructuring, an alias or a call, a name declared twice or after its use, a fallback that is not a whole literal, and a template with other text. In TypeScript, an environment read followed by a non-null mark, a cast or a `satisfies` clause (`process.env.<NAME>!`, `process.env.<NAME> as string`) is not read either. Such a site needs a manual search. From the root of the repository, with `rg`:

	```bash
	rg -i --glob '*.{js,mjs,cjs,jsx,ts,tsx,mts,cts}' 'authorization.{0,60}process\.env|process\.env\.\w*(auth|basic)'
	```

	or in PowerShell:

	```powershell
	Get-ChildItem -Recurse -Include *.js,*.mjs,*.cjs,*.jsx,*.ts,*.tsx,*.mts,*.cts | Select-String -Pattern 'authorization.{0,60}process\.env|process\.env\.\w*(auth|basic)'
	```

	Open each match and check what the variable holds. Where it holds `Basic` followed by an encoded pair, the site is Basic Authentication, and the migration is in [Part C for JavaScript](../migration/part-c-javascript.md) for a JavaScript file or [Part C for TypeScript](../migration/part-c-typescript.md) for a TypeScript file. See [Part A for JavaScript](../migration/part-a-javascript.md#js-018) and [Limits of the tool](03-limits.md#javascript-what-the-tool-reads-and-what-it-does-not).

29. **Browser code and JSX files are read with limits, and a `.jsx` file with unusual markup can be abandoned part-way.** The tool does not parse JSX. A quote inside element text damages only its own line, but a backtick or a block-comment opener inside element text can make the tool read the rest of the file as text, so every match after that point is reported at Low or is not found, and the report counts the file under "Files only partly readable as code, so not analyzed in full". In the measurement, 2 of the 6 `.jsx` files were abandoned part-way for this reason; that is a small number of files and not a rate to rely on. The same happens after a template literal nested more than eight deep and after any unterminated literal or block comment. When a file you expect to produce findings reports only Low ones after some point, or is counted as not fully read, review it by hand from that point. What a browser sends for a credential in an address, in `XMLHttpRequest.open` or in a jQuery call was read from the text of the web platform's specifications and was not run in a browser. A `.tsx` file has the same limit; see known issue 37. See [Part A for JavaScript](../migration/part-a-javascript.md#how-confidence-is-assigned) and [Limits of the tool](03-limits.md#javascript-what-the-tool-reads-and-what-it-does-not).

30. **JavaScript is read as text, one call at a time, and the forms its catalog declares unsupported are not reported.** The tool does not follow an options object, an authentication object or a header object held in a variable, a module or a default export and handed to a client elsewhere, an alias of a client, a wrapper function, a header built by a function call, a computed property name, a generated API client, or a credential assigned in one statement and sent in another. It does not read a request written by hand to a socket, a credentialed address assembled from parts, proxy credentials, a shell command inside an executed string, the runtimes other than Node.js such as Deno and Bun, JavaScript inside other files, a credential held in a `.env`, JSON or YAML file or in `.npmrc`, or the folders the scan never enters (`node_modules`, `dist` and `build`, in lower case). A construct in a dead branch or in a function nothing calls is reported as if it ran, and a test, mock or sample with a neutral name is reported at its full level. A plain `.js` or `.mjs` file is not marked as Node.js, so a server file there that renders a page with a password field into a string is read as interactive and receives Authorization Code although the code acts as itself. A `'Basic ...'` literal held in a variable with no header write in the same statement is not reported, and neither is a header value held in a name the file does not declare exactly once before its use. A custom prompt wrapper and a credential read through a helper are not sign-in evidence the tool lists, so a file whose evidence is of that kind takes the default flow, Client Credentials, although a person may supply the credential. A Node.js script whose only evidence is prompt wording is not read as interactive, because that signal is not read in a Node.js file, so it takes the default flow, Client Credentials, with its note; if such a script acts on behalf of a signed-in user, choose Authorization Code by hand. A prompt function defined locally beyond the reading window may be assigned the interactive flow, Authorization Code, although the code acts as itself. A constant declaration that follows a brace or a semicolon on the same line, and a literal continued over lines by a backslash, are read wrongly, so a name can resolve to the wrong value and a finding can be missed or misplaced. A `URL` object whose scheme is not visible where its user name and password are assigned, such as one built from a parameter, is reported at Medium. A user name or a password written as a bare name is read in the `auth` option of an `axios` or `request` call, and in a credential object that no rule reads in that spelling (a Low `auth` object with no client beside it, a `got` call, a jQuery call) a member is read only when it is written with a key and a colon; an encoder whose first literal ends in a colon and whose second part is code (`btoa('exampleUser:' + secret)`) is not read; and a header value built inside the project's own function, as a template that joins a scheme held in a constant with an encoded pair, is not read at the call, while the function itself is reported at Low. HTML-like comments (`<!--` and `-->`) in a non-module script are not read as comments, so code on such a line is read as code. The tool reads a call up to a window of 1,500 units and a use of a name up to thirty lines after its definition; a call longer than the window, or a use farther than thirty lines away, is not read, and a file that reaches a time limit is counted in the report and its findings are not reported. Search for these by hand with the searches in [Part A for JavaScript](../migration/part-a-javascript.md#declared-unsupported-coverage), and see [Limits of the tool](03-limits.md#javascript-what-the-tool-reads-and-what-it-does-not).

31. **A VB.NET colon-joined pair that `0.3.0-alpha` reported at Medium is not reported now.** One planted pair of the VB.NET benchmark, of a kind the catalog covers, was reported at Medium by `0.3.0-alpha` and is not reported by this release. This is a known regression and it is not corrected in this release. A pair of this kind can be missed, so search for them by hand with the searches in [Part A for VB.NET](../migration/part-a-vbnet.md). See known issue 20 and [Limits of the tool](03-limits.md#vbnet-findings-that-are-not-basic-authentication).

32. **A credential-cache entry is read by the scheme as written, and a mail or proxy credential is found by position.** `cache.Add("<host>", 8080, "Digest", new NetworkCredential(user, password))` is not a Basic entry, and the credential constructed as its last argument is no longer reported as a plain credential construction (`CS-008`). An entry under `Basic` is still reported as `CS-003`, and a credential held in a variable and given to the cache is not affected. A scheme written as an identifier, such as a constant, is read as `CS-003` under that class's own rules, which resolve a constant declared once in the same file (High when it resolves to `Basic`, nothing when it resolves to another scheme, and Medium when it is declared more than once or comes from elsewhere). Separately, the credential constructed inside an entry whose scheme is a literal other than `Basic` or is an identifier is not reported as `CS-008`, and for an identifier this holds even when it holds `"Basic"`, because that rule does not resolve the identifier; the entry itself is then the finding. A related limit, which this release did not change: a mail client or proxy created with an initializer takes the credential bound within the next five lines whatever object that binding names, so a credential bound to another object there is also reported at Low as a mail or proxy credential. Open a Low finding of this kind and check which object receives the credential. See [Limits](03-limits.md#what-the-catalogs-declare-they-do-not-cover).

33. **TypeScript types are read as names in the text, and some typed forms are not read.** The tool does not resolve a type across files, read `tsconfig.json`, follow an import or a path alias, or know what a type alias expands to. The typed forms it reads are the request-configuration types of `axios` and its credentials type; an object typed by any other name, such as a type of your own, a type alias, an import alias or the type of another client, is reported at Low (`JS-011`) where its shape matches, or not at all. A known name followed by an explicit generic argument list is read after `as` and `satisfies` and not after an annotation, a typed default or an angle-bracket assertion; a generic argument list on a call is read only to three levels of nesting, up to 120 characters a level, on one line and with no blank before the opening angle bracket; a `URL` binding written with a type annotation is not read for its user-name and password assignments; and a typed object whose `auth` key follows a nested member such as `headers: { ... }` is not read as typed and is reported at Low. A finding is missed in these forms, so search for them by hand with the searches in [Part A for TypeScript](../migration/part-a-typescript.md#declared-unsupported-coverage).

34. **An injected client is recognized by the name of its receiver.** The tool reads a NestJS `HttpService` call whose receiver name contains `http`, in any letter case, and never the type of the receiver. A client of another type that is held under such a name, an Angular `HttpClient` held as `this.http` for example, and is given an `auth` object with a user name and a password, is reported at High as `TS-003` although it may not send Basic Authentication: review each such finding before you act. A service held under a name without `http`, a call through the service's `axiosRef`, the `auth` option of a module configuration and a call whose receiver and member are split by a line break are missed at High, and the `auth` object is reported at Low where its shape matches. A fetch-based client is not encoded: an `Authorization` header written through it is still read, and an `http`-named client given an `auth` pair may be read at High although that package does not document the pair. The Angular and NestJS names the tool has not checked against their documentation (`HttpClient`, `HttpHeaders`, interceptors, test controllers, the configuration service, routing decorators, and `HttpService` of any package version other than the one checked) are not read.

35. **Some TypeScript type text is reported as a header write, and a typed proxy address is reported as a service address.** A type member written as `{ Authorization: 'Basic' }`, or an `Authorization: 'Basic'` member that ends in a closing brace, a comma or a line end, in an interface or a type alias, cannot be told from a header object written as a value: it is reported at High in a file that is not a declaration file, which is a false positive, and at Low in a declaration file. A member that ends in a semicolon or a single vertical bar is not reported, and neither is a template-literal type whose hole is `string` or `number`. The same member written inside a `headers:` member of a type is reported the same way. A declaration with a type annotation whose value is an address with user information, `const proxyUrl: string = <an address with a user name and a password>`, is reported at Medium as a service address, because the tool reads the word of the annotation and not the declared name that denotes a proxy; a proxy address written without an annotation, under a name that contains `proxy` or `proxies` in any letter case, is not reported: the tool skips such a proxy address by its name only when the declaration carries no type annotation, and with an annotation it reads the type word instead, which is the cost described above. Dismiss such findings on review.

36. **A value followed by a TypeScript tail is read less far.** A header value held in a name is not resolved when the value ends in a non-null mark, a cast or a `satisfies` clause, or when it reads a member access (`this.token`), another name or a call: only a module-level constant or a class field with a literal counts, and the name is then not resolved and nothing is reported. An Angular header object whose value is an identifier (`new HttpHeaders({ Authorization: header })`, `setHeaders: { Authorization: header }`) is not read, while the same name given to `set` or `append` is. A password or a token written as a literal and followed by a cast, a `satisfies` clause or a non-null mark is reported with its class and its level but without the warning that a credential is written into the source; if you use that warning to find the secrets to rotate, search the TypeScript files by hand for credential names followed by a quoted literal. A constant declared after a brace or a semicolon on the same line, a template with a hole, a value followed by an angle-bracket assertion and an annotation that holds an equals sign are not counted as declarations, so a name with one counted and one uncounted declaration can resolve to the wrong value, which is a missed or misplaced finding. For an environment read with a tail, see known issue 28.

37. **A `.tsx` file and a few spellings of TypeScript can damage the reading of the text around them.** The tool does not parse JSX: in a `.tsx` file a backtick or a block-comment opener in element text, or a template literal nested nine deep, makes the tool read the rest of the file as text, so every match after that point is reported at Low or is not found, and the report counts the file under "Files only partly readable as code, so not analyzed in full"; an apostrophe in element text damages only its own line. A postfix non-null mark followed by a slash, with a blank before the mark (`x !/2`), after a closing brace (`}!/2`), doubled (`x!!/2`), in element text, or inside the arguments of a call, and an instantiation expression followed by a division (`id<number> / 2`), are read as the opening of a regular expression; the damage is one line, or, when a later slash on the same line closes it, the code between the two slashes is read as a string, so a construct there can be demoted or missed and the report counts no damage. In a JavaScript file, text that looks like a generic call, a tight chain of comparisons or an explicit type argument with no blank before the opening angle bracket, followed by a credential shape of a class that reads such calls, can be reported, which is a false positive; and a header object whose `Basic` literal is followed by a semicolon, a single vertical bar or the end of an object type can lose its finding. Review a file that reports only Low findings after some point by hand from that point.

38. **Some TypeScript is not read, and a declaration file is read at Low with a sentence that can be wrong.** A script with no extension whose first line names `ts-node`, `tsx` or `deno` is not read, because the tool attributes a language by the extension or by a first line that names an interpreter it lists, and these runners are not listed; search such scripts by hand. TypeScript inside single-file components, HTML templates, notebooks and Markdown documents is not read. Inbound Basic Authentication, a guard, middleware, interceptor or test controller that checks a Basic header, is a different construct and is kept out of the findings by its shape, but a test whose expected header is written as an object literal cannot be told from a header write and is reported at Medium as test code. A Relativity-published TypeScript client or typings, and Relativity's extensibility surfaces, are declared not covered: no class reads a call through either, and raw HTTP is what the tool reads. Search for such calls by hand. A declaration file (`.d.ts`, `.d.mts` and `.d.cts`) is reported at Low for manual review because of its suffix, with the sentence the report writes for a generated file: that is true of a declaration file a compiler produced and not of a hand-written declaration of ambient types, and the tool cannot tell the two apart. The level is right and the sentence can be wrong; judge the match with [Judging a Low-confidence match](../migration/part-c-typescript.md#judging-a-low-confidence-match).

39. **A TypeScript server written as a plain `.ts` file can be assigned Authorization Code, and a form and its call in two files take the default flow.** The Node.js marking separates only a file that declares itself: a `.cts` file or a file whose first line names `node` or `nodejs`. A `.ts`, `.mts` or `.tsx` file is not marked, because an ES module runs in both environments, so a NestJS or Express server written as a plain `.ts` file is read with the browser signals and can be assigned the interactive flow, Authorization Code, although the code acts as itself. A component that holds the form and a service that makes the call are in two files, so the finding takes the default flow, Client Credentials, with the note that asks who supplies the credential, although a person may sign in. Choose the flow by hand where the code acts for a signed-in user, and where a server acts as itself, use Client Credentials. See known issue 8 and [Part C for TypeScript](../migration/part-c-typescript.md#choosing-the-variant-for-your-application).
40. **The method-level class reports methods that store, validate or forward credentials, not only methods that build them.** A method or class that holds a credential, checks one or passes one along, instead of building the header or the credential itself, can be reported by the class for authentication helpers, at Low and for manual review. These findings add noise for the reviewer: expect to dismiss some of them, and judge each one by what the method does with the credential. See [Part C for C#](../migration/part-c-csharp.md#cs-011-judging).

41. **A credential stored in a member is read at the wrong level when a second credential is created on the line that hands it over.** When a credential is stored in a member and later handed to a mail, proxy or file-transfer client, the tool follows it inside a window of 30 lines. If a second credential is created on the same line as that hand-over, before it, the first credential is still read as the low-confidence mail or proxy finding, instead of the medium-confidence network-credential reading that the catalog describes for that case. If you rely on the level to decide what to migrate, check the first credential by hand wherever a hand-over line creates another credential. See [Part A for C#](../migration/part-a-csharp.md#cs-019).

### How to report an issue

Report an issue through the channel this release was distributed with, the place where you downloaded it. Include the version string from `migrate-auth --version`, your platform, the command you ran, and what you expected. **Do not attach a report or a JSON data file to an issue without reading it first:** they contain no credential values, but they list where credentials are in your repository. Never paste a credential.

## Version 0.5.1-alpha

The previous release, `0.5.1-alpha`, is kept here as the history of the tool. Its catalog was version `1.35.0`, it supported C#, PowerShell, VB.NET, Shell and JavaScript, it counted TypeScript files and did not assess them, and the time limit on its matching was 44.25 seconds. Its changes, and those of the release before it, are listed below.

### Changes in 0.5.1-alpha, from 0.5.0-alpha

- **A short file is no longer skipped for taking too long to analyze.** In `0.5.0-alpha`, some files with nothing unusual in them, such as a C# file of a few lines that builds a `NetworkCredential` for an `HttpClientHandler`, ran into the time limit on the tool's matching and were listed under "Files whose analysis took too long and was stopped", so their findings were not reported. The cause was in how some of the tool's search expressions were compiled, and it could affect C#, PowerShell, VB.NET, Shell and JavaScript files. The expressions are now written so that they compile correctly, and they find the same constructs as before. **If a report of `0.5.0-alpha` lists files whose analysis was stopped, run the assessment again with this release.**
- **A session saved by `0.5.0-alpha` is not resumed.** The detection catalog moves to version `1.35.0`, and a session saved under another catalog version is started fresh. See known issue 6.

### Changes in 0.5.0-alpha, from 0.4.0-alpha

- **JavaScript is analyzed.** The tool analyzes JavaScript files: files ending in `.js`, `.mjs`, `.cjs` or `.jsx`, and files with no extension whose first line names `node` or `nodejs`, directly or after `env` and its options. It has seventeen pattern classes, each described in [Part A of the Migration Documentation for JavaScript](../migration/part-a-javascript.md), with the constructs the catalog declares unsupported. The migration suggestion for each class and each flow is in [Part C for JavaScript](../migration/part-c-javascript.md). The report and the JSON data file name the class of a JavaScript finding with an identifier from `JS-001` to `JS-017`. Five of the classes, `JS-007`, `JS-009`, `JS-011`, `JS-014` and `JS-016`, are always Low and always go to manual review. **A repository whose JavaScript files were counted and not analyzed in an earlier release can now report JavaScript findings.** Test code in JavaScript is reported at Medium at most, as in the other languages. JavaScript written inside other files, such as HTML script elements, single-file components of frameworks and templates, is not read; search those files by hand with the searches in Part A. **A clean JavaScript result does not cover them, and it does not cover a credential that lives in a `.env` file or in another configuration file.**
- **The recommendations for JavaScript name the kind of application they are for.** The tool does not know whether a file runs in a browser or in Node.js, so the Authorization Code recommendation has a variant for a browser, a Node.js server and a Node.js command line, and the Client Credentials recommendation has a variant for a Node.js process and one for browser code that does not act for a signed-in user. Each variant opens with the condition it is for; keep the one that describes your code.
- **The browser findings ask a few things of the client.** Code that runs in a browser is delivered to the person using it, so a credential written into it has been public for as long as the code has shipped, and the recommendation says to treat it as compromised and to rotate it. A browser never holds the client secret or a token: the call to RelativityOne moves behind a server-side component that performs the token exchange and keeps the tokens, and that component must authenticate and authorize its own callers. See [Part C for JavaScript](../migration/part-c-javascript.md#choosing-the-variant-for-your-application) and the JavaScript notes in [Part B](../migration/part-b-secret-management.md#javascript-bundles-browser-storage-and-the-server).
- **TypeScript files are counted and not assessed.** Files ending in `.ts`, `.tsx`, `.mts` or `.cts` appear in the scan summary and have no findings. A finding in a language that is not delivered yet, TypeScript, Python or Go, is not reported, and **an empty result for those languages does not mean that no Basic Authentication was found.**
- **The time limit on the tool's matching is 44.25 seconds, raised from 15.25.** The JavaScript files that take longest to analyze, long lines packed with encoder calls, need more time than the other languages do. See known issue 9.
- **The `lowReasons` value `demotedFile` is retired.** The tool does not write it, and a saved session that carries it is not resumed. A Low finding in a demoted file names the kind of file, as in 0.4.0-alpha.
- **A session saved by `0.4.0-alpha` is not resumed.** The detection catalog moves to version `1.34.0`, and a session saved under another catalog version is started fresh. See known issue 6.

## Version 0.4.0-alpha

The previous release, `0.4.0-alpha`, is kept here as the history of the tool. Its catalog was version `1.31.0`, it supported C#, PowerShell, VB.NET and Shell, and the time limit on its matching was 15.25 seconds. Its changes, and those of the releases before it, are listed below.

### Changes in 0.4.0-alpha, from 0.3.0-alpha

- **Shell is analyzed.** The tool analyzes Shell scripts: files ending in `.sh`, `.bash`, `.zsh` or `.ksh`, and files with no extension whose first line names `bash`, `sh`, `zsh` or `ksh`. It has twenty-five pattern classes, each described in [Part A of the Migration Documentation for Shell](../migration/part-a-shell.md), with the constructs the catalog declares unsupported. The migration suggestion for each class and each flow is in [Part C for Shell](../migration/part-c-shell.md). The report and the JSON data file name the class of a Shell finding with an identifier from `SH-001` to `SH-025`. Seven of the classes, `SH-011`, `SH-012`, `SH-015`, `SH-017`, `SH-020`, `SH-022` and `SH-023`, are always Low and always go to manual review. **A repository whose Shell files were counted and not analyzed in an earlier release can now report Shell findings.** The dialects the tool does not read are declared out: `fish`, `csh` and `tcsh` scripts and Windows batch files are not Shell here, and neither are shell commands written inside other files, such as CI pipeline definitions, Dockerfiles, Makefiles, crontabs, service unit files and Markdown documents. **In practice many `curl -u` lines live in those files, so a clean Shell result does not cover them: search them by hand.**
- **Test code is reported at Medium, not at Low.** This changes the result for C#, for PowerShell, for VB.NET and for Shell. A finding in a file that the tool recognizes as test code, by its folder, its file name or a test-framework marker, is reported at Medium at most, with the recommendation of its class and a flow, and it counts toward the Medium total. Before, such a finding was Low and had no recommendation. **A repository with Basic Authentication in its tests will see those findings move from Low to Medium.** Medium is the ceiling for test code: a construct that is reported at High elsewhere is reported at Medium when it sits in test code. A mock, fake or stub stays Low; the tool recognizes a mock by its file or folder name and by nothing else, so a mock with a neutral name that sits in test code is reported at Medium. A file that is test code and also a mock, a sample, vendored or generated stays Low. Part A lists the signals for [C#](../migration/part-a-csharp.md#how-confidence-is-assigned), for [PowerShell](../migration/part-a-powershell.md#how-confidence-is-assigned), for [VB.NET](../migration/part-a-vbnet.md#how-confidence-is-assigned) and for [Shell](../migration/part-a-shell.md#how-confidence-is-assigned), and Part C says how to judge a test finding.
- **Every finding in the JSON data file carries `testCode`.** It is `true` when the file's name, folder or a test-framework marker marks it as test code, and `false` otherwise. The Markdown report states it on a `Test code` line under the finding's heading and writes nothing for a finding that is not test code.
- **The reason for a Low finding names its kind.** The `lowReasons` values gain `demotedMockFile`, `demotedSampleFile`, `demotedGeneratedFile` and `demotedDeploymentFolder`, and the report says in words which kind of file it is. The value `demotedFile` is kept so that a data file written by an earlier release can be read, and this release does not write it. The two Low classes of VB.NET, `VB-018` and `VB-019`, now say why they are Low, as the C# and PowerShell ones do.
- **VB.NET reads encoded pairs, headers and the Import API constructor more exactly.** A user name and password joined with a character-literal colon (`":"c`) is read as an encoded pair, inside the call that encodes it and in a pair built before it. A token carried under the Basic scheme is read when the colon is first or last in an interpolated string, when `String.Concat` or `String.Join` continues its arguments on the next line with ` _`, and when `vbNullString` is the first operand inside the encoder call. An encoded pair is reported only where its second half carries a credential word, so a pair whose second half is held under a name such as `pin` is no longer reported as an encoded pair. The credential words end at the boundary of their spelling, so `relayPassHeader` is read and `Bypass` is not. The Import API constructor is not reported when your own type of the same name is declared close by, and a system token returned by a call is not read as its password. A file whose only construct is the type of an authentication header value is now read. See known issues 20 and 21.
- **The time limit on reading strings and comments also covers Shell arithmetic.** The limit of 1000 milliseconds that applies to the reading of the strings and comments of a file during `analyze` now includes the read-ahead that decides whether a double parenthesis in a Shell script opens arithmetic. A file that spends the budget keeps the findings before the point where it was spent and reports none at or after it, as described in known issue 9.
- **The time limit on the tool's matching is 15.25 seconds, lowered from 22.75.** See known issue 9.
- **A session saved by `0.3.0-alpha` is not resumed.** The session format moves to schema 9, which adds the marker of test code on each finding and the reasons that name a kind of file. See known issue 6.

### Changes in 0.3.0-alpha, from 0.2.0-alpha

- **VB.NET is analyzed.** The tool analyzes VB.NET source files (`.vb`), with nineteen pattern classes, each described in [Part A of the Migration Documentation for VB.NET](../migration/part-a-vbnet.md), with the constructs the catalog declares unsupported. The migration suggestion for each class and each flow is in [Part C for VB.NET](../migration/part-c-vbnet.md). The report and the JSON data file name the class of a VB.NET finding with an identifier from `VB-001` to `VB-019`. Two of the classes, `VB-018` and `VB-019`, are always Low and always go to manual review.
- **A PowerShell file that assigns the Base64 result of a user-and-password pair is no longer skipped.** Before, a script that assigned the encoded pair to a variable and was followed by ten or more lines could reach the tool's time limit, so that the tool discarded every finding of the file and counted the file as one whose analysis took too long. Such a file is now analyzed and reports its findings.
- **A C# interpolated string that writes a literal brace as `{{` is read correctly.** Before, the first brace of the doubled opener was read as the start of an expression, so the tool could misread the rest of the string and the code after it. A finding below such a string could be reported at the wrong level or missed.
- **The report says when the configuration disabled a language.** When the repository configuration disables a language that has files in the repository and the report lists findings, the summary now names that language under the findings table. Before, it said so only when there were no findings.
- **The report says when the minimum confidence level hides a finding that carries a literal credential.** The console warns about such a finding; the report does not list it, and the summary now says how many there are and how to list them.
- **The reason given for a PowerShell web command called with `-Credential` and no scheme is worded more carefully.** It now says that the call is not sent as Basic to a server that answers with a bearer challenge, as RelativityOne does, and that it is sent as Basic to a server that asks for Basic, so you confirm where the call points.

### Changes in 0.2.0-alpha, from 0.1.1-alpha

- **PowerShell is analyzed.** The tool analyzes PowerShell scripts, with fourteen pattern classes, each described in [Part A of the Migration Documentation for PowerShell](../migration/part-a-powershell.md), with the constructs the catalog declares unsupported. The migration suggestion for each class and each flow is in [Part C for PowerShell](../migration/part-c-powershell.md). The report and the JSON data file name the class of a PowerShell finding with an identifier from `PS-001` to `PS-014`.
- **The C# catalog reads more forms.** It reads more of the ways a C# credential or client can be written, such as a type name written with its namespace in front of it, and more of the ways a header value can be built, such as a scheme held in a constant written with its type name in a header-enumeration write. [Part A for C#](../migration/part-a-csharp.md) lists the classes, and [Limits of the tool](03-limits.md#what-the-catalogs-declare-they-do-not-cover) lists the forms that are still not read.
- **The time limit on the tool's matching is 22.75 seconds, and the first-line check and the reading of strings and comments have a limit of 1000 milliseconds, raised from 250.** See known issue 9.

## Version 0.1.1-alpha

The release `0.1.1-alpha` is kept here as the history of the tool. Its catalog was version `1.6.0`, it supported C# only, and the time limit on its matching was 5.25 seconds.

### Changes from 0.1.0-alpha

- **A key in the configuration file with a value that is not valid no longer discards the rest of the file.** Before, a `defaultFlow` such as `"Client Credentials"` (instead of `ClientCredentials`) in the user profile file made the tool use the built-in defaults for every setting, so the report was written to the folder the tool was started from instead of the configured `outputPath`. Now only that key is ignored, as if it were absent; a warning at start-up names the key (and the value, when it is text), and the other settings in the file still apply. A file that is not valid JSON, is not a JSON object or is too large is still reported at start-up and not applied: each of its settings is taken from the next source. See [The configuration file](01-using-the-tool.md#the-configuration-file).
