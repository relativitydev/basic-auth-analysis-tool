# Limits of the tool (User Guide, section 3 of 8)

This section says what the tool does not do, how well it did on its test repository, and what a result does and does not mean. Read it before you rely on a report.

## Languages delivered so far

This release analyzes **C#, PowerShell, VB.NET, Shell, JavaScript and TypeScript**. The other two languages of the plan (Python and Go) are delivered one at a time; see [What's next](02-release-notes.md#whats-next).

**Files in languages that are not delivered yet are not analyzed. An empty result for them does not mean that no Basic Authentication was found.** Python and Go files are counted in the scan summary and are not assessed, and a finding in a Python or Go file is not reported. The scan summary of the report counts those files so that you can see how many there are. The same holds inside C# and PowerShell: the tool reports what its catalogs search for, and a run with no findings means that none of the constructs the catalogs cover was found in the C#, PowerShell, VB.NET, Shell, JavaScript and TypeScript files it could read. A run that finds nothing completes normally, with exit code 0, and its report says that it found zero findings.

## Folders the walk does not enter

The walk does not enter seven folder names, matched exactly and in lower case at any depth: `obj`, `.git`, `.vs`, `node_modules`, `dist`, `build` and `packages`. It also does not enter a folder named `bin` that has a project file (`.csproj`, `.vbproj` or `.fsproj`) beside it, because that is where a build leaves its output; a `bin` folder with no project file beside it is read like any other folder. Nothing in an excluded folder is read, so hand-written code or scripts kept in a folder with one of those names, or in a `bin` folder beside a project file, are not assessed. The report names the excluded folders and counts them, so the gap is visible; they are not skipped items. No other folder name is excluded. See [What the scan reads and what it leaves out](01-using-the-tool.md#what-the-scan-reads-and-what-it-leaves-out).

## Files that are too large

The tool analyzes a file only if it is at most 2 MiB (2,097,152 bytes) and its longest line has at most 10,000 characters. A file above either limit is not analyzed at all, and the report counts it under **Files larger than this release analyzes** or **Files with a line longer than this release analyzes** and names it. Review such a file by hand. A minified or machine-written file is the usual cause.

## Text encodings

The tool reads a source file as UTF-8, UTF-16 or UTF-32 (the last two with a byte order mark, and UTF-16 also without one). A file that is none of these is read as **Windows-1252**, which covers Latin-1 and the other Western European files, and the report counts and names these files so that the reading is never silent. The tool cannot tell which single-byte code page a file was written in, so a file in another one, such as a Cyrillic or Central European code page, is read with its non-ASCII characters changed, or is counted as a file that could not be read as text when it holds a byte Windows-1252 leaves undefined. A credential written in plain ASCII is found either way. See the [release notes](02-release-notes.md#known-issues).

## What the catalogs declare they do not cover

Each catalog declares what it does not cover, and the report prints the same list in its Coverage section. The lists are in [Part A for C#, Declared unsupported coverage](../migration/part-a-csharp.md#declared-unsupported-coverage), [Part A for PowerShell, Declared unsupported coverage](../migration/part-a-powershell.md#declared-unsupported-coverage), [Part A for VB.NET, Declared unsupported coverage](../migration/part-a-vbnet.md#declared-unsupported-coverage) [Part A for Shell, Declared unsupported coverage](../migration/part-a-shell.md#declared-unsupported-coverage), [Part A for JavaScript, Declared unsupported coverage](../migration/part-a-javascript.md#declared-unsupported-coverage) and [Part A for TypeScript, Declared unsupported coverage](../migration/part-a-typescript.md#declared-unsupported-coverage). A construct on a list produces no finding; review those areas by hand, or search for them with the patterns in Part A.

**C#.** The list includes code in Razor views and in other .NET languages, credentials in configuration files, credentials passed through dependency injection or configuration binding, a user name and password written into a URL, calls made by compiled libraries, a conditional-compilation block in a file that also holds an interpolated raw string or a raw string opened with more than one `$` (read as live code), and files in single-byte code pages other than Windows-1252. The forms below are the ones this release's catalog declares as not read, so check them by hand:

- **A scheme held in a named constant written with its type or namespace in front of it** is not read when it is the scheme argument of a credential-cache entry, of an `AuthenticationHeaderValue` or of a header written by name (`CS-003`, `CS-005`, `CS-006`), nor in the concatenated and interpolated spellings of `CS-006`. It is read in a header-enumeration write (`CS-012`). A constant that carries both the scheme and the space and is concatenated directly with the credential, and a `string.Format` over the constant, are not read.
- **A type, client or credential renamed with a `using` alias**, or an enumeration member or conversion reached through `using static` without its type, is not recognized, and a file that does nothing else is missed. The spellings with the namespace written in front of the type name are read.
- **A credential or client created with the short `new(...)` form**, where the type name does not stand in front of the variable (an assignment to an existing variable, a return, an argument or a property initializer), is not read. The form with the declared type in front of the variable is read where [Part A](../migration/part-a-csharp.md) says so.
- **A credential cache entry added by a collection initializer**, and **a credential created by an object initializer that carries both the user name and the password in the one initializer**, are not read by the classes for those constructs, so a file that holds only such a construct can be missed.
- **A password control reached through a call with a nested call in its argument, a constructed operand or a parenthesized operand** (`Find(Get("x")) as PasswordBox`) is not used as evidence that a person signs in. The finding is then decided as if that evidence were absent, which can only move the result toward the default flow.
- **A mail, file-transfer, directory or proxy credential whose client is renamed with a `using` alias, or is created with the short `new(...)` form where the type name does not stand in front of the variable,** is reported at Medium as a plain credential construction and not at Low as a non-HTTP credential, because the client's type name is not in the text. A file-transfer request is read as the non-HTTP case whether it is obtained from `WebRequest.Create(...)` or from `FtpWebRequest.Create(...)`, and whether its type is given by a cast in front of the call or by `as FtpWebRequest` after it.
- **A credential-cache entry is read by the scheme as written.** `cache.Add("<host>", 8080, "Digest", new NetworkCredential(user, password))` is not a Basic entry, and the credential constructed as its last argument is not reported. An entry under `Basic` is reported as `CS-003`, and a credential held in a variable and given to the cache is not affected. A scheme written as an identifier, such as a constant, is read as `CS-003` under that class's own rules, which resolve a constant declared once in the same file (High when it resolves to `Basic`, nothing when it resolves to another scheme, and Medium when it is declared more than once or comes from elsewhere). Separately, the credential constructed inside an entry whose scheme is a literal other than `Basic` or is an identifier is not reported as a plain credential construction, and for an identifier this holds even when it holds `"Basic"`, because that rule does not resolve the identifier; the entry itself is then the finding.
- **A mail client or proxy created with an initializer, and a credential bound a few lines later, is found by position.** `new SmtpClient(host, port) { EnableSsl = true };` followed within five lines by `.Credentials = new NetworkCredential(user, password)` is reported at Low as a credential for a client that is not an HTTP client. The tool does not check that the binding names the same variable, so a credential bound to another object in those five lines is read the same way. Open a Low finding of this kind and check which object receives the credential.
- **The standard library's Base64 conversion called without its type name** through a `using static` directive is not read as the end of a credential pair.
- **A call to the Relativity helper method named GetProxy that passes a user name and a password in a form the tool does not read:** two arguments with no sign of a user or a password in their names (a text second argument counts only when the first is also text or named like a user), a second argument that names both a token and a password, a different number of arguments, a call written without a type argument, a type argument that is not a single type name (one level of nested type arguments is read), an argument written as an expression more complex than a name, a member access, a single call or an index, or named arguments written in reverse order. The tool reports this call only when the second argument is named like a password, or the first argument is named like a user, or both arguments are written as text, and it never reports it when the second argument is named like a token or a key. Other calls that send a user name and a password are not reported, so search for `GetProxy` and review each call by hand. A call of an unrelated method with the same name and similar arguments can be reported, and should be dismissed on review.
- **A settings object that sets the Relativity API user name and password pair, two members whose names start with `Rsapi`, in a form the tool does not read:** the two members more than five lines apart or in different files, one member in an initializer and the other assigned separately, the password set before the user name, a nested brace or more than 600 characters between the two members of one initializer, different middle parts in the two names, the same extra prefix before `Rsapi` in both, or a value that is a calculation rather than a name, a call or text. The tool reads the pair only when both members are set next to each other in one of the two plain forms; a pair set any other way can still send a user name and a password and is not reported, so search for `Rsapi` and review each settings object by hand. A declaration written over two lines can be reported as if it set the pair.
- **A type of another library with the same simple name as the Relativity SDK credentials type is reported at High.** The tool recognizes the Relativity credentials type by the name as it is written, and does not check which library the type comes from, so a type of another library, or of your own, with that name and built from a user name and a password is reported at High as `CS-001` although it is not a Relativity credential. Check the library of every such finding and dismiss the ones that do not come from the Relativity SDK.
- **Some genuine C# findings are reported at Low.** A colon-joined user name and password that is encoded to Base64 is reported at Low when neither half is named like a user name or a password, which includes two neutral names and names that use a credential word the tool does not list; it stays at Medium when a half is named so, and a composite key with a half named like a user, a login or an account is then a false finding you can dismiss on review. Code in a block that the file's own conditional-compilation symbols switch off is reported at Low, and so is a genuine use that is built only under a symbol that the project file or the build command defines, or under a build symbol outside the list the tool treats as supplied by a build, because the tool does not read the project file or the build command. A Low finding goes to manual review with no flow and no recommendation, and the report names the reason; read every one before you dismiss it.
- **A credential stored in a member of a settings object and later handed to a mail, proxy or file-transfer client, in a form the tool does not follow:** the client created before the credential is stored, more than 30 lines apart or across a line longer than 400 characters, a client held in a field or a parameter, the member written differently or copied through a variable first, a credential created inside an initializer or held in a single variable, any line between the two that contains the word `NetworkCredential`, such as another credential, a declaration or a comment, or the same member also handed to an HTTP client elsewhere in the file. The tool follows the credential only inside the window and the forms described in its entry. Outside them the credential is reported as an ordinary network credential at medium confidence, which is a false finding when it goes to a mail, proxy or file-transfer server, so confirm the destination of every such finding. A credential also handed to an HTTP client in the same file may not be reported at that place, so review the HTTP use by hand. A client or a hand-over written inside a comment or a text can be taken for real code.

**PowerShell.** The list in Part A has the full text. In short, the tool does not read:

- credentials, flow evidence, a header table or a header scheme that comes from another file: a dot-sourced script, an imported module, a loaded configuration or data file, a value passed in as a parameter, a splatted table defined more than twenty lines before its use or built at run time, and defaults supplied through `$PSDefaultParameterValues`; and secret-store commands other than the three the tool lists;
- a credential object created in a form it cannot see: a hashtable cast or `-Property` on an SDK credential type, reflection or a computed type name, a credential built in one statement and assigned to a handler by variable, an SDK entry point built directly from a user name and a password;
- a header written with a key or a value held in a variable that does not name the scheme close by, and a scheme held in a variable that cannot be read as a constant: the finding is then kept at a lower level, so a Bearer header held that way can be reported as a possible Basic header and should be dismissed on review;
- a user name and password written into a URL, Basic Authentication performed by a program the script calls (`curl.exe -u`, `wget --user`), and Basic Authentication through other stacks that take the credential as a parameter, such as a COM request or `Start-BitsTransfer -CustomHeaders`;
- a header declared as text and converted into a table at run time (`ConvertFrom-StringData`, `ConvertFrom-Json`), which is reported only through its Base64 step, when one is visible;
- PowerShell data and configuration files (`.psd1` manifests, DSC documents, `.ps1xml`, `.psc1`, `.cdxml`, `.mof`), PowerShell inside another file type, and any code inside an `Add-Type -TypeDefinition` here-string, a `-Command` string or an `Invoke-Expression` argument: the inner code is read as the text of its string;
- a command name written so that the tool cannot read it: a backtick inside the name, a computed name invoked with `&`, a user-defined alias for a web cmdlet;
- a call written inside the `$( ... )` of an expandable here-string (`@"` ... `"@`), and a string delimited by a typographic quote other than the two pairs the tool reads, which can make the tool misread the rest of the file;
- a script in a single-byte code page other than Windows-1252 (see [Text encodings](#text-encodings)).

**VB.NET.** The list in Part A has the full text. In short, the tool does not read:

- **Visual Basic 6, VBA, VBScript and other Basic dialects.** Files ending in `.vbs`, `.bas`, `.cls`, `.frm` or `.vbhtml`, and classic ASP, are a different language from VB.NET. The tool does not attribute them to VB.NET, and they stay in the list of files that were not assessed, so a repository whose Basic Authentication is in such files needs a hand search.
- **VB.NET written inside markup.** The server-side script blocks and the inline code of `.aspx`, `.ascx` and `.master` files are not scanned. The code-behind file of the same page, which ends in `.aspx.vb`, is.
- **XML literals**, and any code inside them. An apostrophe in their text is read as a comment, and an odd double quote can make the tool read the rest of the file as text.
- **A string delimited by a mixed pair of typographic quotes**, a typographic interpolated string, and an `Authorization` header key written between typographic quotes.
- **Code inside a disabled conditional-compilation branch.** The tool reads a block under a `#If` condition that is false as code, so a construct in it is reported as if it were live. This differs from C#: the reading that reports a switched-off C# block at Low, and a colon-joined pair whose halves carry no credential word at Low, is not applied to VB.NET, and the PowerShell and VB.NET readings of a colon-joined pair are unchanged in this release.
- credentials, a scheme or flow evidence supplied from another file (a partial class or module, a code-behind page whose markup holds the login control, project-level imports, a loaded configuration file), and credentials in configuration files such as `app.config`, `web.config`, `.settings` files, `appsettings.json` and `.resx` resources;
- a credential or a client created in a form the tool cannot see: an SDK credential created by an object initializer, reflection or `Activator.CreateInstance`, a type renamed with an `Imports` alias of the type, a credential built across statements, a credential built with a domain as its third argument, and arguments written out of order with names;
- a user name and password joined by a colon and encoded by the project's own Base64 helper, an encoder called without its type name, or a separator held in a constant; a user name and password written into a URL; and Basic Authentication performed by a native program the code starts;
- an `Authorization` header written with a value held in a variable or a parameter whose name carries no credential word;
- a source file saved in a single-byte code page other than Windows-1252 (see [Text encodings](#text-encodings)).

**Shell.** The list in Part A has the full text. [Shell: what the tool reads and what it does not](#shell-what-the-tool-reads-and-what-it-does-not) says what each item means for a result.

**JavaScript.** The list in Part A has the full text. [JavaScript: what the tool reads and what it does not](#javascript-what-the-tool-reads-and-what-it-does-not) says what each item means for a result, and starts with the one that most needs a search of your own: an `Authorization` header whose whole value comes from an environment variable.

### Variables inside double-quoted strings

In PowerShell only `$( ... )` inside a double-quoted string is read as code. A variable written as `$name` or `${name}` inside such a string is read as part of the string's text. No construct can hide in a bare variable name, so detection is not affected, but a `${...}` whose name itself contains a quote character can end the string early for the tool and not for PowerShell, and the tool then reads the rest of the string wrongly.

## Accuracy thresholds and what was measured

The tool is measured against a benchmark test repository that holds planted Basic Authentication patterns and deliberate near-misses (constructs that resemble Basic Authentication and are not). The targets are these:

| Measure | Target |
| --- | --- |
| Recall on planted patterns the catalog claims to support | at least 90 % reported at High or Medium |
| False-positive rate on near-misses | at most 10 % reported at High or Medium |
| Recall floor for each language | at least 80 % |
| Recommendation coverage | 100 %: every High or Medium finding carries a recommendation for its flow |
| Flow-assignment accuracy | at least 90 % overall and at least 90 % for each expected flow |

These are NSerio's recommended starting thresholds. They have not been confirmed by Relativity.

### What the figures cover

The figures below were measured for `0.3.0-alpha`, on its detection catalog (catalog `1.19.0`), for C#, for PowerShell and for VB.NET. Since then the tool has begun to report test code at Medium at most instead of Low (test code that is also a mock, a sample, vendored or generated stays Low), has corrected how VB.NET is read, and has added Shell, JavaScript and TypeScript, and the figures below are those of the `0.3.0-alpha` measurement; the measurement of this release is not published here, apart from the bounded measurement of the three C# corrections of `0.6.1-alpha`, given under C# below: **no figure is stated for Shell, for JavaScript or for TypeScript, and the VB.NET figures predate the VB.NET corrections.** They were measured on Windows and on Linux, and the two runs produced byte-identical results. The Linux run used a virtual machine on the same computer as the Windows run, so it is another operating system and not other hardware. **The measurement on macOS is pending.** Percentages are rounded to one decimal. Beside each rate the tables give the lower end of its 95 % Wilson confidence interval, because the populations are small.

**The PowerShell judgement is bounded, not confirmed.** The PowerShell catalog rests on one real repository, which holds very few cases. The planted items of the benchmark were written from the same documentation the catalog describes. So the figures say how consistent the tool is with its own catalog. They do **not** say how it performs on real scripts. A separate small set of 12 deliberately tricky near-miss scripts, written to be hard for a matcher that reads one file at a time, had 7 of 12 = 58.3 % reported at High or Medium. That is far above the rate in the tables, and it shows that the near-misses of the benchmark are easier than adversarial ones.

**"Blind" has a narrow meaning here.** A set of planted items is blind when it was planted without sight of the tool's signal expressions or of the analyzer source. It does **not** mean blind to the catalog. A figure on a blind set still measures consistency with the catalog.

### VB.NET

**The VB.NET judgement is bounded, not confirmed.** No VB.NET repository was available to calibrate the catalog. It was written from Relativity's and Microsoft's documentation and from C# code converted to VB.NET, and the planted items of the benchmark were written from the catalog. So the figures say how consistent the tool is with its own catalog. They do **not** say how it performs on real VB.NET code.

The older set was used afterwards to decide what to correct, so what the corrections fixed in it is not independent evidence. ## Low confidence needs review

A finding at **Low** confidence is present in the text but unlikely to be live authenticating code: a comment, a documentation string, a mock, fake or stub, sample or example code, vendored code, or a generated file. **Test code is not Low:** a finding in a file the tool recognizes as test code is reported at Medium at most, with a recommendation, and the report marks it as test code; a file that is test code and also a mock, a sample, vendored or generated is Low. Two more causes exist for C#: a colon-joined pair that is encoded to Base64 and whose halves are not named like a user name and a password, and code in a block that the file's own conditional-compilation symbols switch off; and one for JavaScript and TypeScript, an `Authorization` header whose value is read from a settings property. Sample and example code means a folder named `sample`, `samples`, `example` or `examples`, or a file whose name begins with `Sample` or `Example`; vendored code means a folder named `vendor` or `third-party`. A sample kept under another name, such as a folder called `demo`, is not recognized and is reported at its ordinary level. A folder named `Deployment` lowers a C# finding to Low and does not lower a PowerShell, a VB.NET, a Shell, a JavaScript or a TypeScript finding: a script or source file under that folder is reported at its full level. Part A lists every signal, for [C#](../migration/part-a-csharp.md#how-confidence-is-assigned), for [PowerShell](../migration/part-a-powershell.md#how-confidence-is-assigned), for [VB.NET](../migration/part-a-vbnet.md#how-confidence-is-assigned), for [Shell](../migration/part-a-shell.md#how-confidence-is-assigned), for [JavaScript](../migration/part-a-javascript.md#how-confidence-is-assigned) and for [TypeScript](../migration/part-a-typescript.md#how-confidence-is-assigned). The tool gives a Low finding no flow and no recommendation and routes it to manual review. It is not evidence that the code does not authenticate. [Part C](../migration/part-c-csharp.md#judging-a-low-confidence-match) explains how to judge each cause.

## The flow is chosen from the finding's own file

The flow is decided for each file, not for each finding and not for the repository: the tool decides between Client Credentials and Authorization Code from signals in the same file as the finding, and only there, and every finding of one file takes that file's flow. A login page, a login handler or a credential prompt in a different file is not seen, and neither is a script dot-sourced or a module imported by a PowerShell script, and neither is a credential that arrives through dependency injection or configuration binding, nor the markup of a web page whose code-behind is the file being read. In real code the credential usually reaches the finding's file from another file, so **`Default` is the expected decision for most real integrations**: the finding gets the default flow, and its note asks you who supplies the credential at run time. That is not a failure of the tool; it is the reason the note exists. [Confirming the flow](../migration/part-c-csharp.md#confirming-the-flow) in Part C explains how to decide by hand, and [Part C for Shell](../migration/part-c-shell.md) does the same for a Shell script. Pointing to evidence found elsewhere in the same repository is planned after the alpha.

## A script with both a stored credential and a prompt

When one file holds both interactive evidence (a credential prompt such as `Get-Credential`, a console prompt for a secret, a desktop password control) and fixed-credential evidence (a stored credential read from the environment, from a credential file or from a secret store, or a credential built from a plain-text value), the tool assigns **Authorization Code** to the file. The same rule applies to C#. A common PowerShell script reads a stored credential and falls back to `Get-Credential` only when none is stored: it runs unattended in its normal use, so Client Credentials is usually the better choice, and the tool recommends Authorization Code for it anyway. The note on the finding asks you who supplies the credential at run time; answer it, and apply the other flow where the script normally runs without a person. [Confirming the flow](../migration/part-c-powershell.md#confirming-the-flow) in Part C for PowerShell explains how to decide by hand. A Shell script that reads a credential from the environment and falls back to a silent `read -s` when it is unset is resolved in the same way, to Authorization Code; [Confirming the flow](../migration/part-c-shell.md#confirming-the-flow) in Part C for Shell explains how to decide by hand.

## VB.NET: Web Forms pages and a file with both kinds of evidence

**A Web Forms page is decided by its code-behind alone.** A page whose login control is declared in the `.aspx` markup and whose code is in the `.aspx.vb` file reaches the tool as the code-behind file only, because the markup is not scanned. If the code-behind holds no login handler of its own, the finding takes the default flow, Client Credentials, although the page acts for a signed-in user. The same happens to any VB.NET file whose evidence of how a user signs in is in another file, such as a partial class or a module defined elsewhere. For code that serves a signed-in user, use Authorization Code whatever the tool recommended. [Confirming the flow](../migration/part-c-vbnet.md#confirming-the-flow) in Part C for VB.NET explains how to decide by hand.

**A file that holds interactive evidence and fixed-credential evidence receives Authorization Code.** This is the same rule as in the other languages, and in VB.NET it also reaches a file that merely contains two unrelated pieces of code, one that serves a signed-in user and one that runs unattended, such as a module that holds both a login handler and a scheduled job. If the match is in the unattended part, Client Credentials is the right flow. The note on the finding asks who supplies the credential at run time; answer it and apply the other flow where the code normally runs without a person.

## VB.NET: how the tool reads quotes and conditional blocks

**A double quote the tool does not see closed turns the rest of the file into text.** When the tool reads a VB.NET file it marks where each comment and string begins and ends. A stray or odd double quote, for example inside an XML literal, inside a long string that the tool pairs differently from the compiler, or inside a block switched off with `#If`, can make it read everything after that point as the inside of a string. Every match after the quote is then reported at Low, with no flow and no recommendation. If a VB.NET file reports Low findings below some line and you expect higher ones, look for an unbalanced double quote above that line, fix or review it, and read the file by hand from there.

**A disabled `#If` branch is read as code.** The tool does not evaluate conditional compilation. A block under a condition that is false, such as `#If False Then`, is read like any other code, so a construct in it is reported at its ordinary level although it is never compiled. A double quote in such a block can also end the analysis of the rest of the file, as described above. Check whether the branch is built before you migrate a finding in it.

## VB.NET findings that are not Basic Authentication

The tool reports some VB.NET code that does not perform Basic Authentication towards RelativityOne, and misses or classes differently a few forms that do. Each item says what you see and what to do.

- **A credential handed to a consumer the tool does not know is reported at Medium.** A `NetworkCredential` built for a share, a mail server, a directory or a library whose consumer the tool does not list is reported as an unaccounted credential (`VB-013`). A credential whose receiver is named for a share or a mail service is reported the same way. Dismiss the finding if the consumer is not RelativityOne.
- **A system token given to the Import API constructor can be reported as a user and password.** A token-named argument, and a token returned by a call whose name carries `Token`, are declined as the password of the constructor; a call whose own argument holds a further call (`FetchPlatformToken(Resolve(scope))`) is still reported. A type of your own with the same name as the SDK's Import API type is not reported when it is declared as a class or a structure in the same file, close to the use, and written without a namespace; a type declared in another file or farther than about one thousand characters away is still reported by that class and by the SDK credential classes. Check that the second argument is a password.
- **A variable that holds a bearer value under a name that carries `token` is reported as a Basic header value.** A header write whose value sits in a variable is read when the variable's name carries a credential word; a name that carries `bearer` or `access_token` is read as a bearer and is not reported, and other token names are. Check what the variable holds.
- **A host joined by a colon to a value that is not a port can be reported as an encoded pair**, and a value held under a name declared in two procedures of one file can be read as the credential of the other. Dismiss such a finding on review.
- **A colon-joined pair that `0.3.0-alpha` reported at Medium is not reported now.** One planted pair of the VB.NET benchmark, of a kind the catalog covers, was reported at Medium by `0.3.0-alpha` and is not reported by this release. This is a known regression and it is not corrected in this release; a pair of this kind can be missed, so search for them by hand with the searches in [Part A for VB.NET](../migration/part-a-vbnet.md). See the [release notes](02-release-notes.md#known-issues).
- **A pair whose second half is held under a name with no credential word is not reported as an encoded pair.** The second half is read only when its name carries a credential word, such as `password`, `secret`, `credential` or `token`, or `pass`, `pwd` or `apikey` as a whole word, so a half held under `pin` or `passphrase` is not read; a header value that names the scheme next to the conversion is still reported. An `Authorization` header whose value is held in a variable whose name carries `pass`, `pwd` or `apikey` in lower case followed directly by a digit, such as `pass2`, is not reported, while the same name with a capital first letter, `Pass2`, is. Search for these forms by hand with the searches in [Part A for VB.NET](../migration/part-a-vbnet.md).
- **The check that declines a name and a size or a port is not applied in every spelling.** A half ending in `Length`, `Count`, `Size` or `Port` is declined only in some spellings of the pair: it is not applied to a first half ending in `Length`, `Count` or `Size` joined with `&` or `+`, to a half followed by `.ToString()`, to a second half ending in `Port` written inside the encoder call, or to a second half ending in `Length`, `Count` or `Size` written inside the encoder call with `&`, `+`, an interpolated string or `String.Concat`. In those spellings a name and a size or a port can be reported as an encoded pair when the second half carries a credential word. Dismiss such a finding on review.

## Shell: what the tool reads and what it does not

A Shell script is a program that sends a credential by calling an HTTP client, and the tool reads the call as text, without running or parsing the script. Each item says what you see and what to do. [Part A for Shell](../migration/part-a-shell.md#declared-unsupported-coverage) has the full list the report prints.

- **One family of shells is read.** The tool reads `bash`, `sh` (POSIX, usually `dash`), `zsh` and `ksh`. Scripts for `fish`, `csh` and `tcsh` and Windows batch files (`.bat`, `.cmd`) are different languages: they are not attributed to Shell and stay in the list of files that were not assessed.
- **Shell inside other files is not read, and much of it is there.** A CI pipeline definition, a Dockerfile, a Makefile, a crontab, a service unit file or a Markdown document that holds shell commands is not a shell script, so its commands are not analyzed. In practice many `curl -u` lines live in such files. Search them by hand with the searches in Part A.
- **Some shell files are not attributed to Shell.** `.bats` test files, shell start-up files such as `.bashrc`, `.bash_profile`, `.profile`, `.zshrc`, `.zshenv` and `.envrc`, and a script with no file extension whose first line does not name `bash`, `sh`, `zsh` or `ksh`, in lower case, as the interpreter, directly or after `env` and any options written as one word, such as `dash`, `ash`, `mksh`, `ksh93` or `busybox sh`, or that puts a separate argument word or a variable assignment between `env` and the shell, stay in the list of files that were not assessed, and the report names them. The first line is read only for a file with no extension: a file ending in `.sh`, `.bash`, `.zsh` or `.ksh` is read whatever its first line names, and a file with any other extension is not attributed to Shell by its first line.
- **A credential in a file the script only reads is not seen.** The contents of a `.netrc`, a `.curlrc`, a `.wgetrc` or an `.env` file are not in the text the tool analyzes, and that is where a credential usually lives. A configuration that the script writes itself is read. A header, a token or a scheme that another script supplies through `source` is not joined to its use, and neither is sign-in evidence in a sourced file.
- **Code that is never sent is not reported, and code that never runs is.** A credential built into a variable, an array or a pair is reported only when a call to a known client uses it within the next thirty lines, so a pair that is only printed or compared is not reported. A construct in a dead branch (`if false`), after an `exit`, or in a function that nothing calls and that uses no parameter is reported as if it ran, because the tool does not know the order of execution.
- **A command that runs from a string is read in the listed forms.** The tool reads the commands in `eval`, `bash -c` and the other shells with `-c`, `su -c`, `ssh host "..."`, a backtick or `${...}` inside a double-quoted string, and a here-document fed to a shell. A command in another form (the stage after a pipe on a continuation line, a script written to a file and run by a separate command, `bash < file`, a process substitution, a here-string, a shell behind `env`, `nohup` or `exec`, a quoted command word) is text to the tool and is reported at Low. A Low match inside a quoted command may be live code.
- **Four forms are read the way `bash` reads them.** A here-document terminator written with ANSI-C quoting, one continued across a backslash and a line feed, one quoted across a line feed, and a here-document opened inside a command substitution that closes on the opening line are read differently by `dash`, and the last also by `bash` before 5.2. In those forms the lines after the here-document can be read as its body where the shell runs them as commands.
- **An array of command options that is very long is not read.** The text of an array, from its opening parenthesis to its closing one, is read when it is on one line of up to 10,000 characters or on up to thirty lines of at most 400 characters each. A longer array that holds a credential option is not reported. Search such an array by hand with the search in Part A.
- **Two limits are silent.** More than 5,000 here-document openings waiting for their bodies in one region of a file, and an arithmetic double parenthesis whose closing is hidden by a here-document body or is past the per-file read-ahead budget, are read without any message. The time the tool spends on the strings and comments of a Shell file, arithmetic included, is limited to 1000 milliseconds; see [A file that takes too long](#a-file-that-takes-too-long).
- **A mock or a test with a neutral name is not recognized.** The tool recognizes test code by a folder, a file name or a test-library marker, and a mock by a folder or a file name. A mock with a neutral name is reported at the level of its class and may be a false positive; a test with a neutral name outside every test folder is reported as production code.
- **The destination is not known.** The tool sees a command line and cannot tell whether a call goes to RelativityOne or to another server. Such findings are reported with a note that they may not apply when the destination is not RelativityOne.
- **A shell script that prompts a person is read as interactive.** A script that reads from the environment and falls back to `read -s` is assigned Authorization Code, as described in [A script with both a stored credential and a prompt](#a-script-with-both-a-stored-credential-and-a-prompt).

## JavaScript: what the tool reads and what it does not

A JavaScript file sends a credential through an option of an HTTP client, a header, the user information of an address or an encoder, and the tool reads that call as text, without running or parsing the code. Each item says what you see and what to do. [Part A for JavaScript](../migration/part-a-javascript.md#declared-unsupported-coverage) has the full list the report prints.

- **An `Authorization` header whose value is read from an environment variable is reported at Low for review, and some forms are not reported.** This is a limit of what the code shows. A header written as `headers: { Authorization: process.env.<NAME> }` (or with `import.meta.env`, `Deno.env.get` or `Bun.env`), alone, with a `||` or `??` fallback, or with the value first copied into a variable in the same file, is reported at Low for manual review: the scheme is inside the variable, and the tool cannot tell from the code whether it is `Basic`. A fallback literal that begins with `Basic` is a Basic header written in the code itself and is reported at High; a fallback that begins with `Bearer` is not reported. A site is not reported when an explicit `Bearer` value for an `Authorization` header is written within thirty lines of it, before or after; the tool reads text and not code there, so a comment or a string that spells the header with a `Bearer` literal also hides the site, and so does a `Bearer` fallback of any environment read in the window. These forms are not reported at all: a chain of fallbacks, a read with optional chaining, a read held through another variable, a destructuring, an alias or a call, a name declared twice or after its use, a fallback that is not a whole literal, and a template with other text; in TypeScript, an environment read followed by a non-null mark, a cast or a `satisfies` clause (`process.env.<NAME>!`) is not read either. A site like this needs a manual search. Run it from the root of the repository, and open each match to see what the variable holds:

	```bash
	rg -i --glob '*.{js,mjs,cjs,jsx,ts,tsx,mts,cts}' 'authorization.{0,60}process\.env|process\.env\.\w*(auth|basic)'
	```

	```powershell
	Get-ChildItem -Recurse -Include *.js,*.mjs,*.cjs,*.jsx,*.ts,*.tsx,*.mts,*.cts | Select-String -Pattern 'authorization.{0,60}process\.env|process\.env\.\w*(auth|basic)'
	```

	Where the variable holds `Basic` followed by an encoded pair, the site is Basic Authentication and needs the migration in [Part C for JavaScript](../migration/part-c-javascript.md) for a JavaScript file or [Part C for TypeScript](../migration/part-c-typescript.md) for a TypeScript file. The same holds for a header value that a function returns or that another file supplies.
- **What the tool reads.** JavaScript files are those ending in `.js`, `.mjs`, `.cjs` or `.jsx`, and files with no extension whose first line is a shebang that names `node` or `nodejs`. TypeScript files (`.ts`, `.tsx`, `.mts`, `.cts`) are read as TypeScript; see [TypeScript: what the tool reads and what it does not](#typescript-what-the-tool-reads-and-what-it-does-not). JavaScript inside other files (HTML script elements, single-file components of frameworks, templates) and the runtimes other than Node.js, such as Deno and Bun, are not read as JavaScript; search such files by hand with the searches in Part A.
- **Browser code and JSX are read with limits.** The tool does not parse JSX. A quote inside element text damages only its own line, but a backtick or a block-comment opener inside element text can make the tool read the rest of the file as text: every match after that point is reported at Low or is not found, and the report counts the file under "Files only partly readable as code, so not analyzed in full". On the `.jsx` files of the measurement, 2 of 6 were abandoned part-way for this reason and none was skipped whole; that is a small population and not a rate to rely on. A file with unusual markup should be reviewed by hand from the point where the reading stopped. The same happens to a template literal nested more than eight deep and to any unterminated literal or block comment.
- **A browser's request is read from the code, not run.** What a browser sends for a credential in an address, in `XMLHttpRequest.open` or in a jQuery call rests on the text of the web platform's specifications and was not run in a browser. These calls (`JS-009`, `JS-014`, `JS-016`) send the credential only after a server challenges for it, and the tool reports them at Low for manual review, so that you see them. Part A explains each.
- **A client is recognized by its name.** The tool knows `axios`, `request`, `superagent`, `got`, `node-fetch`, `undici`, jQuery and the Node.js `http` and `https` modules, with `fetch` and `XMLHttpRequest`. The behaviour of these clients rests on their documentation at the version read, and no third-party client was installed or run. An options object, an authentication object or a header object held in a variable, a module or a default export and handed to a client elsewhere, an alias of a client, a wrapper function, a header-setting method of a client the catalog does not list, and a generated API client are not followed. A credential assigned in one statement and sent in another is not joined, and a computed property name (`headers[name]`) is not read.
- **Some more forms are not read.** A `'Basic ...'` literal held in a variable with no header write in the same statement is not reported, and neither is a header value held in a name the file does not declare exactly once before its use. A custom prompt wrapper and a credential read through a helper are not sign-in evidence the tool lists, so a file whose evidence is of that kind takes the default flow, Client Credentials, although a person may supply the credential. A Node.js script whose only evidence is prompt wording is not read as interactive, because that signal is not read in a Node.js file, so it takes the default flow, Client Credentials, with its note; if such a script acts on behalf of a signed-in user, choose Authorization Code by hand. A prompt function defined locally beyond the reading window may be assigned the interactive flow, Authorization Code, although the code acts as itself. A constant declaration that follows a brace or a semicolon on the same line, and a literal continued over lines by a backslash, are read wrongly, so a name can resolve to the wrong value and a finding can be missed or misplaced. A `URL` object whose scheme is not visible where its user name and password are assigned, such as one built from a parameter, is reported at Medium. HTML-like comments (`<!--` and `-->`) in a non-module script are not read as comments, so code on such a line is read as code. The tool reads a call up to a window of 1,500 units and a use of a name up to thirty lines after its definition; a call longer than the window, or a use farther than thirty lines away, is not read.
- **Some forms are not read.** A request written by hand to a socket, a quoted carrier key (`'headers'` in quotes, reported at Low), a credentialed address assembled from parts, a header written to undici as a flat array, proxy credentials (`Proxy-Authorization`), and a shell command inside an executed string such as a `curl` command given to `child_process`. An encoder more than 300 characters from the word `Basic` or `Authorization` is read at the header if at all. Text that looks like a generic call (a tight chain of comparisons, or an explicit type argument with no blank before the opening angle bracket) followed by a credential shape can be reported, which is a false positive, and a header object whose `Basic` literal is followed by a semicolon, a single vertical bar or the end of an object type can lose its finding. Search for these by hand.
- **An `Authorization` header whose value is a settings property is reported at Low only in the form the tool was shown, and the other forms are not reported.** A header written as `headers: { Authorization: settings.serviceAuthorization }`, where the file assigns a property of that name (a name that ends with `authorization`) from an environment variable whose name has a credential word in it (`auth`, `token`, `secret`, `credential`, `key`, `pass` or `basic`), is reported at Low for manual review. The property is joined by its name alone, so a name assigned twice in the file, a literal assignment of the same name and a class field of the same name with an initializer hide the use; a member that only declares a type (`name: string;`, `name: AuthHeader`) is not an assignment and hides nothing. One residual limit: the last member of an object literal whose value is a bare name or a dotted path with no trailing comma (`name: otherValue` followed by a line that closes the object) cannot be told from a type declaration, so it is read as a type and is not counted, and a property assigned twice may then not hide the use. A property under another name (`auth`, `authHeader`), bracket access, destructuring, optional chaining, an object shorthand, a call as the receiver, several members on one line, a class field assigned from an environment value, a property filled from a call, an alias or another file, an environment variable named for a host or a port, and a property whose fallback names a scheme are not reported. In TypeScript, a property or an environment read followed by a non-null mark or a cast is not reported either. Search for these by hand.
- **Two forms are declared as not covered and give no finding at any level.** A user name and a password joined by a colon and given to the project's own encoder function, in a file that never names the Basic scheme, is not reported, because the tool recognizes the standard encoders only and a function of the project's own gives it nothing to anchor on. A credential, options or header object that is chosen by a selector (an enumeration, a switch or a map) and returned from a function, with no client visible in the same statement, is not reported either, because the tool does not follow a value from where it is chosen to where it is used. Neither is offered as a Low reading, since there is no scheme word, carrier, client or encoding in the text to report. Search for the project's own encoding helpers and for functions that return credentials or client options by hand.
- **A bare member name is read for `axios` and `request` only, and a split encoder pair only when both parts are literals.** A user name or a password written as a bare name in the `auth` option of an `axios` or `request` call is read. In a credential object that no rule reads in that spelling (a Low `auth` object with no client beside it, `got`, jQuery) a member is read only when it is written with a key and a colon. An encoder whose first literal ends in a colon is read when the second part is a literal too, and not when it is code (`btoa('exampleUser:' + secret)`), because the second part is then hard to tell from a host and port or a cache key. A header value built inside the project's own function, as a template that joins a scheme held in a constant with an encoded pair, is not read at the call, and the function itself is reported at the Low level. Review such code by hand.
- **Where the credential lives is not read.** `.env` files, JSON and YAML configuration and `.npmrc` are not in the text the tool analyzes, and a credential usually lives there. A credential assembled across modules is not joined to its use.
- **Code that is never sent is reported when it is written.** A construct in a dead branch, or in a function nothing calls, is reported as if it ran. A test, mock, sample or vendored file with a neutral name is reported at its full level and can be a false positive; a mock is recognized only by its folder or file name.
- **The flow is chosen from the file.** A plain `.js` or `.mjs` file is not marked as Node.js, because an ES module runs in both environments, so the browser signals are read there, and a plain `.js` server file that renders a page with a password field into a string is read as interactive although the code acts as itself. A password typed in another module is not seen. See [The flow is chosen from the finding's own file](#the-flow-is-chosen-from-the-findings-own-file).
- **Files that are not read, and a few that are read oddly.** A file with a line longer than 10,000 characters, which includes a minified single-line bundle, is skipped whole and counted. The folders `node_modules`, `dist` and `build` are not entered, in lower case; `Dist` and `BUILD` are read, and a generated tree under them is reported at its full level. A regular expression written after a closing parenthesis, a closing brace or a comment is read as a division and its text as code; the Unicode line and paragraph separators damage the reading around them.
- **The destination is not known.** The tool sees a call and cannot tell whether it goes to RelativityOne or to another server. Such findings are reported with a note that they may not apply when the destination is not RelativityOne.

## TypeScript: what the tool reads and what it does not

A TypeScript file is read with the rules of JavaScript, as text and without running or compiling the code, and two classes exist for TypeScript alone. Each item says what you see and what to do. [Part A for TypeScript](../migration/part-a-typescript.md#declared-unsupported-coverage) has the full list the report prints, and the limits of [JavaScript](#javascript-what-the-tool-reads-and-what-it-does-not) apply to TypeScript text as they do to JavaScript, among them the `Authorization` header whose whole value comes from an environment variable.

- **What the tool reads.** TypeScript files are those ending in `.ts`, `.tsx`, `.mts` or `.cts`, and declaration files (`.d.ts`, `.d.mts` and `.d.cts`), which are reported at Low for manual review with no recommendation and no flow; [Judging a Low-confidence match](../migration/part-c-typescript.md#judging-a-low-confidence-match) says how to judge them. TypeScript inside other files (single-file components, HTML templates, notebooks and Markdown documents) is not read; search such files by hand with the searches in Part A.
- **A script with no extension that is run by `ts-node`, `tsx` or `deno` is not read.** The tool attributes a language by the extension, or by a first line that names an interpreter it lists, and these runners are not listed. Search such scripts by hand.
- **A declaration file is read at Low with a sentence that can be wrong.** The report gives a declaration file the sentence it writes for a generated file. That is true of a declaration file a compiler produced and not of a hand-written declaration of ambient types; the level is right, the sentence can be wrong, and the tool cannot tell the two apart.
- **Inbound Basic Authentication is not what the tool reads.** A guard, middleware, interceptor or test controller that checks a Basic header is kept out of the findings by its shape, but a test whose expected header is written as an object literal cannot be told from a header write and is reported at Medium as test code. A Relativity-published TypeScript client or typings, and Relativity's extensibility surfaces, are declared not covered: no class reads a call through either, and raw HTTP is what the tool reads. Search for such calls by hand.
- **Types are read as names in the text.** The tool does not resolve a type across files, read `tsconfig.json`, follow an import or a path alias, or know what an alias expands to. An object typed by a name the tool does not know is not read as typed: it is reported at Low where its shape matches, or not at all. The typed forms the tool reads are the request configurations of `axios` and the credential type of `axios`. A known name followed by an explicit generic argument list is read after `as` and `satisfies` and not after an annotation, a typed default or an angle-bracket assertion; a generic argument list on a call is read only to three levels of nesting, up to 120 characters a level, on one line and with no blank before the opening angle bracket; a `URL` binding with a type annotation is not read for its user-name and password assignments; and a typed object whose `auth` key follows a nested member such as `headers: { ... }` is reported at Low. A finding is missed in these forms; search for them by hand.
- **A user name or a password written as a bare name is read in a few objects.** In TypeScript the `axios` and `request` option rules, the typed credential object (`TS-001`) and the NestJS service call (`TS-003`) read a member written as a bare name (`{ username, password }`); in a credential object that no rule reads in that spelling a member is read only when it is written with a key and a colon, and `TS-003` reads only the members `username` and `password`, so an object with `user` and `pass` is reported at Low.
- **An injected client is recognized by the name of its receiver.** The tool reads a NestJS `HttpService` call whose receiver name contains `http`, and never the type of the receiver. A client of another type held under such a name, an Angular `HttpClient` held as `this.http` for example, that is given an `auth` object with a user name and a password is reported at High although it may not send Basic Authentication: review each such finding. A call on a receiver with another name, a call through the service's `axiosRef`, the `auth` option of a module configuration and a call whose receiver and member are split by a line break are missed at High, and the credential object in it is reported at Low where its shape matches. A fetch-based client is not encoded, and an `http`-named client given an `auth` pair may be read at High although that package does not document the pair. The Angular and NestJS names the tool has not checked against their documentation are not read.
- **Some type text is reported as a header write.** A type member written as `{ Authorization: 'Basic' }`, or an `Authorization: 'Basic'` member that ends in a closing brace, a comma or a line end, in an interface or a type alias, cannot be told from a header object written as a value: it is reported at High in a file that is not a declaration file, a false positive, and at Low in a declaration file; the same holds inside a `headers:` member of a type. A member that ends in a semicolon or a single vertical bar is not reported. A declaration with a type annotation whose value is an address with user information, `const proxyUrl: string = <address>`, is reported at Medium although the name denotes a proxy, because the tool reads the annotation's word and not the name; dismiss such findings on review.
- **Browser code and `.tsx` files are read with limits.** The tool does not parse JSX, so a backtick or a block-comment opener inside element text can make the tool read the rest of the file as text: every match after that point is reported at Low or is not found, and the report counts the file under "Files only partly readable as code, so not analyzed in full". Review such a file by hand from the point where the reading stopped. A postfix non-null mark followed by a slash, written with a blank before the mark, in a doubled mark, after a closing brace, in element text or inside the arguments of a call, and an instantiation expression followed by a division, can damage the reading of one line, and when a later slash on the same line closes the regular expression the tool thinks it sees, the code between the two slashes is read as a string and a construct there can be demoted or missed with no damage counted. A template literal nested nine deep, or a backtick or a block-comment opener in element text, abandons the rest of the file.
- **Two forms are declared as not covered and give no finding at any level.** A user name and a password joined by a colon and given to the project's own encoder function, typed or not, in a file that never names the Basic scheme, and a credential, options or header object chosen by a selector (a TypeScript enumeration, a switch or a map) and returned from a function with no client visible in the same statement, are not reported, for the reasons given for JavaScript above. Search for them by hand.
- **A header value with a TypeScript tail is not read in some forms.** A header value held in a name is not read when the value ends in a non-null mark, a cast or a `satisfies` clause, and an environment read followed by a non-null mark or a cast (`process.env.NAME!`, `process.env.NAME as string`) is not read. An Angular header object whose value is an identifier is not read, while the same name given to `set` or `append` is. A password or a token written as a literal followed by a cast, a `satisfies` clause or a non-null mark is reported with its class and level but without the warning that a credential is written into the source. A constant declared after a brace or a semicolon on the same line, a template with a hole, and a value followed by an angle-bracket assertion are not counted as declarations. Search for these by hand.
- **A test, mock or sample with a neutral name is reported at its full level.** The tool recognizes test code by a folder, a file name or the `describe` and `it` calls, and a mock by a folder or a file name, so a neutral name is read as production code and can be a false positive. TypeScript has no file name that marks a bundle as generated, and a file with a line longer than 10,000 characters is skipped whole and counted.
- **The flow is chosen from the file.** A plain `.ts`, `.mts` or `.tsx` file is not marked as Node.js, because an ES module runs in both environments, so a NestJS or Express server written as a plain `.ts` file is read with the browser signals and can be assigned Authorization Code although the code acts as itself. The Node.js marking separates only a `.cts` file and a file whose first line names `node` or `nodejs`. A form held in a component and a call made in a service are in two files, so the finding takes the default flow. See [The flow is chosen from the finding's own file](#the-flow-is-chosen-from-the-findings-own-file).
- **Where the credential lives is not read.** `.env` files, Angular environment files, JSON and YAML configuration and `.npmrc` are not in the text the tool analyzes, and a credential usually lives there.
- **The destination is not known.** The tool sees a call and cannot tell whether it goes to RelativityOne or to another server. Such findings are reported with a note that they may not apply when the destination is not RelativityOne.

## The literal-credential warning is read from where the credential sits

The warning that a credential is written literally into the source depends on the position of the text, not on what it says. A credential construct inside a string, such as a help message or an example shown to the user, can raise the warning although no credential is in use. A literal credential inside a comment raises none, so a commented-out credential is not flagged. Check each warning against the line it names, and search the repository by hand for credentials left in comments.

In Shell, a value that the shell expands (`$`, a backtick, a backslash, a brace, a glob character or a leading `~`) is never a literal credential, so a call such as `curl -u "$API_USER:$API_PASSWORD"` is reported at its level and raises no warning, and neither does a value read with `read`. A password written as a bare word or in single quotes, in a user option, an address, a header, an encoding pipeline or a configuration the script writes, does raise it.

The warning is also not raised when a PowerShell password is written as a quoted literal and passed through `ConvertTo-SecureString '<literal>' -AsPlainText`, wrapped in a credential object and given to `-Credential`. The tool does not follow `-Credential` back to the literal, so the finding is reported at its level with no literal-credential warning, whereas `New-Object System.Net.NetworkCredential('<user>', '<password>')` and a hard-coded Basic `Authorization` header do raise it. If you use the warning to find the secrets to rotate, you will miss these: search the PowerShell files by hand for `ConvertTo-SecureString` used with `-AsPlainText`, and rotate each password written into a script. [Part A for PowerShell](../migration/part-a-powershell.md#declared-unsupported-coverage) gives a search.

## The findings limits

The tool limits how many findings it reports: **2,000 for one file and 50,000 for one scan**. These limits are a bound on pathological or generated input, such as a generated file with an enormous number of matches. An ordinary repository produces a few dozen findings, far below them, so you should never meet a limit in ordinary use. If you do see a notice that findings were counted and not listed, a generated or machine-written file is the likely cause. The report states how many findings each limit removed. The findings that are kept are the first ones in a fixed order (by path for a whole scan, by position for one file), the findings that are dropped are not named or located individually, and the counts stay correct. Find the file that produced the notice in the report, and review it by hand.

## A file that takes too long

The tool bounds the time it spends evaluating each of its search expressions on a file, currently 112 seconds. If a file reaches the limit, the tool discards every finding for that file and counts the file in the report's skipped items, so the loss shows up as a number. Review that file by hand.

Two shorter limits, of 1000 milliseconds each, apply to the first-line check of a file during `scan` and to the reading of its strings and comments during `analyze`; in a Shell script the second also covers the read-ahead that decides whether a double parenthesis opens arithmetic. A file that reaches the first is identified by its extension instead of its first line, and is counted in the report; a file that reaches the second keeps the findings found before the point where the limit was reached, reports none at or after it, and is counted in the report's skipped items. All the limits are provisional; see the [release notes](02-release-notes.md#known-issues).

## File names in decomposed Unicode form

The tool identifies a file by its path as the platform returns it, with the separators normalized. It does not convert file names to a single Unicode normalization form. Two file names that differ only in normalization form are therefore reported as **two files**. A name that reaches the tool in decomposed form, that is an accented letter stored as a letter plus a combining accent, may be positioned and identified differently from the same repository scanned on another platform. This applies on **Windows (NTFS)**, where such a name can exist, on **Linux**, whose file systems keep a name byte for byte and can therefore hold a decomposed name or two spellings of one name, and on **macOS**, which returns some names in decomposed form. Finding identifiers and the order of findings can then differ between platforms for those files. Detection within each file is not affected. The findings of a scan that reaches the limit of 50,000 findings are the exception: the ones kept are the first in path order (see [Limits on the number of findings](#the-findings-limits)), path order depends on the normalization form, and so the findings kept can differ between platforms.
